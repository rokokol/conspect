# Протокол ICMP

## Служебный протокол IP [1:18:39](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=4719s)

> [!note] **ICMP** (Internet Control Message Protocol, протокол управляющих сообщений интернета) — служебный протокол, которым узлы и маршрутизаторы сообщают об ошибках доставки и проверяют достижимость
> Пользовательских данных не переносит. Описан в [[RFC]] 792 и обязателен для любой реализации [[IP-адрес и маска подсети|IP]]

Сообщение ICMP кладётся прямо в IP-пакет, без транспортного заголовка, с [[Заголовок IPv4#Поле Protocol [1 15 35](https //www.youtube.com/watch?v=5iMhAOFx38c&t=4535s)|полем Protocol]], равным `1`:

```
[IP-заголовок, Protocol = 1][ICMP-заголовок][данные]
```

| Признак | IP | ICMP |
|---|---|---|
| Роль | доставка данных | диагностика доставки |
| Несёт | [[Протокол UDP\|UDP]], [[Заголовок TCP и установление соединения\|TCP]] и другие | ошибку, недостижимость, эхо |
| Между кем | процессами, через [[Порты и сокеты\|порты]] | узлами сети, портов нет |

> [!faq]- К какому уровню относить ICMP — сетевому или транспортному
> **За сетевой уровень.** RFC 792 называет ICMP "an integral part of IP". Портов и процесса-получателя нет, работает он между узлами и обслуживает маршрутизацию, а не приложения. Так классифицируют учебные курсы Cisco и Таненбаум
>
> **За транспортный.** Если группировать по полю Protocol, ICMP (`1`) оказывается рядом с TCP (`6`) и UDP (`17`) — "всё, что лежит поверх IP", без различия между переносом данных и служебной сигнализацией
>
> Формальный критерий — есть ли доставка между процессами. У ICMP её нет, поэтому строгая классификация склоняется к сетевому уровню[^lecturer-l4]

[^lecturer-l4]: Лектор перечисляет ICMP вместе с UDP и TCP как протоколы транспортного уровня [1:03:50](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=3830s) — то есть проводит границу по полю Protocol

## Формат сообщения [1:19:44](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=4784s)

| Поле | Размер | Что несёт |
|---|---|---|
| Type | 1 байт | тип сообщения |
| Code | 1 байт | уточнение внутри типа |
| Checksum | 2 байта | контрольная сумма всего ICMP-сообщения |
| Rest of Header | 4 байта | зависит от типа: идентификатор и номер у эха, [[MTU и фрагментация\|MTU]] следующего хопа у Fragmentation Needed, адрес шлюза у Redirect |
| Data | переменный | зависит от типа |

Лектор объединяет последние два поля в "данные, содержимое которых зависит от пары Type и Code" — смысл тот же: всё после контрольной суммы трактуется по типу

> [!note] Сообщение об ошибке несёт начало пакета, который её вызвал
> Маршрутизатор, отбросивший пакет, собирает **новый** IP-пакет: источник — его собственный адрес, назначение — отправитель исходного пакета, `Protocol = 1`. В поле данных — IP-заголовок отброшенного пакета и как минимум первые 8 байт его содержимого. Этих 8 байт хватает на порты [[Протокол UDP|UDP]] или [[Заголовок TCP и установление соединения|TCP]], и [[Операционная система|ОС]] отправителя по ним находит, какому [[Порты и сокеты|сокету]] ошибка адресована

Ошибка на ошибку не порождается: ICMP-сообщение об ошибке не отправляется в ответ на другое ICMP-сообщение об ошибке, на широковещательный или групповой пакет и на любой фрагмент, кроме первого. Иначе один сбой мог бы размножиться лавиной

## Типы сообщений [1:20:48](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=4848s)

| Type | Code | Сообщение | Кто и когда шлёт |
|---|---|---|---|
| 0 | 0 | Echo Reply | узел, получивший Echo Request |
| 3 | 0 / 1 | Destination Unreachable: сеть / узел недостижим | маршрутизатор без маршрута; маршрутизатор последнего хопа, не дождавшийся [[Протокол ARP\|ARP]]-ответа от получателя |
| 3 | 3 | Port Unreachable | узел-получатель: на UDP-порту никто не слушает |
| 3 | 4 | Fragmentation Needed and [[MTU и фрагментация\|DF]] Set | маршрутизатор перед линком с меньшим MTU |
| 3 | 13 | Communication Administratively Prohibited | маршрутизатор или межсетевой экран, отбросивший пакет по правилу |
| 5 | 0–3 | Redirect | маршрутизатор: к этому адресату короче через другой шлюз того же сегмента |
| 8 | 0 | Echo Request | кто угодно, проверка достижимости |
| 11 | 0 | Time Exceeded: [[Заголовок IPv4\|TTL]] истёк в пути | маршрутизатор, обнуливший TTL |
| 11 | 1 | Time Exceeded: истёк таймаут сборки фрагментов | узел-получатель |
| 12 | 0 | Parameter Problem | узел, не сумевший разобрать заголовок |

### Эхо-запрос и ping [1:20:48](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=4848s)

Утилита `ping` отправляет **Echo Request** (type 8), получатель обязан ответить **Echo Reply** (type 0) с теми же идентификатором, номером и данными. Пришёл ответ — узел достижим, а разница времён даёт задержку туда и обратно. Потеря первого пинга в новой сети — работа [[Протокол ARP#Почему теряется первый ping [34 17](https //www.youtube.com/watch?v=HxGsA6Ps-T8&t=2057s)|ARP]], а не проблема сети

ICMP-эхо меряет только сеть: отвечает ядро ОС, приложение в этом не участвует. Если TCP-рукопожатие с тем же узлом кратно медленнее пинга, а потерь ICMP нет, путь исправен, а страдает именно установка соединений — теряются или придерживаются [[Заголовок TCP и установление соединения|SYN]]. Так сравнение ICMP и TCP и служит диагнозом

### Fragmentation Needed и PMTUD [1:21:50](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=4910s)

Пакет с поднятым [[MTU и фрагментация|DF]] не влезает в MTU следующего линка — маршрутизатору остаётся только отбросить его и отправить назад type 3 code 4[^ptb]. Во второй половине поля Rest of Header лежит **MTU того линка**, через который пакет не пролез (RFC 1191) — на этом построен [[MTU и фрагментация#Path MTU Discovery [1 11 29](https //www.youtube.com/watch?v=6iEZOuH75cw&t=4289s)|Path MTU Discovery]]

Потерять это сообщение по дороге — значит сломать [[MTU и фрагментация|PMTUD]] молча: соединение устанавливается, а крупные пакеты пропадают. Туннели натыкаются на это чаще всего — расчёт MTU для WireGuard показывает, сколько байт съедает инкапсуляция

[^ptb]: Лектор называет это сообщение "packet too big" [1:22:22](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=4942s). В ICMP для IPv4 оно называется Fragmentation Needed and DF Set; [[NDP и ICMPv6|Packet Too Big]] — имя аналогичного сообщения ICMPv6

### Time Exceeded [1:26:08](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=5168s)

Маршрутизатор, уменьшивший [[Заголовок IPv4#Время жизни пакета [1 14 02](https //www.youtube.com/watch?v=5iMhAOFx38c&t=4442s)|TTL]] до нуля, отбрасывает пакет и шлёт отправителю type 11 code 0. Посылая пакеты с TTL 1, 2, 3 и собирая эти ответы, [[TTL, маршрутные петли и traceroute#ICMP Time Exceeded и traceroute [60 41](https //www.youtube.com/watch?v=l9F567JS-5o&t=3641s)|traceroute]] узнаёт адреса маршрутизаторов на пути

### Недостижимость [1:27:41](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=5261s)

- пакет отброшен [[MTU и фрагментация|ACL]] на маршрутизаторе или межсетевом экране — отправителю может вернуться "заблокировано административно" (type 3 code 13). Видно, что проблема не в связности, а в политике
- пакет дошёл до маршрутизатора, который не знает, куда его передать дальше, — возвращается Destination Unreachable, и ОС отправителя показывает его как "no route to host" [1:28:41](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=5321s)

## Нагрузка на маршрутизатор и фильтрация ICMP [1:29:12](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=5352s)

> [!warning] ICMP-сообщения маршрутизатор генерирует центральным процессором
> Пересылка идёт аппаратно, а каждый Time Exceeded или Fragmentation Needed — работа процессора. Злоумышленник, заваливающий роутер пакетами, на которые положено отвечать ICMP, может истощить его процессор

Поэтому ICMP ограничивают [1:30:13](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=5413s):

- **rate limit** или policing — не больше заданного числа сообщений в секунду; в Cisco IOS, например, `ip icmp rate-limit unreachable`
- блокировка полностью или частично — по типам

Кроме нагрузки, ICMP режут из-за разведки сети пингом и исторической памяти об атаках: Smurf — эхо-запросы на широковещательный адрес с подделанным адресом жертвы, Ping of Death — собранный из фрагментов эхо-пакет длиннее 65 535 байт

> [!danger] Блокировка ICMP целиком ломает служебные механизмы
> Правило "запретить весь ICMP" не различает типы:
> - type 8, Echo Request — ping; блокировка извне оправдана
> - type 3 code 4, Fragmentation Needed — нужен [[MTU и фрагментация#Path MTU Discovery [1 11 29](https //www.youtube.com/watch?v=6iEZOuH75cw&t=4289s)|PMTUD]], к разведке отношения не имеет
> - type 11, Time Exceeded — traceroute
> - type 3 code 3, Port Unreachable — быстрый отказ вместо долгого таймаута
>
> Правильно фильтровать точечно: пропускать диагностические типы и ограничивать скорость эхо-запросов, а не закрывать протокол целиком

## ICMP, IGMP и ICMPv6 [1:31:49](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=5509s)

> [!warning] ICMP и IGMP — разные протоколы
> **IGMP** (Internet Group Management Protocol, протокол управления группами интернета) — созвучный, но другой протокол: им узлы подписываются на [[Типы адресации|multicast]]-группы. `Protocol = 2`, в курсе не рассматривается

В IPv4 ICMP теоретически можно отключить, и сеть "как-то, но живёт" [1:32:19](https://www.youtube.com/watch?v=HxGsA6Ps-T8&t=5539s). В IPv6 без него не работает ничего: ARP там нет, и разрешение адресов, как и поиск маршрутизаторов, выполняют сообщения [[NDP и ICMPv6|ICMPv6]]
