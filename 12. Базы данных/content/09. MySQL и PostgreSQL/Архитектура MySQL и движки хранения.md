# Архитектура MySQL и движки хранения
MySQL — это **ядро** (разбор и планирование запроса) плюс **подключаемое хранилище** (движок, который физически держит данные на диске). За гибкость "выбери движок под таблицу" платят слабым [[Программный интерфейс приложения|API]] между ними и **дублированием метаданных** [00:14:45](https://www.youtube.com/watch?v=mkI2q6twyc0&t=885s)
![[Архитектура MySQL.png]]

## Два слоя: ядро и хранилище
> [!info] Движок запросов знает всё, хранилище — "глупое" [00:01:08](https://www.youtube.com/watch?v=mkI2q6twyc0&t=68s)
> - **Ядро** (движок запросов) знает метаданные всех баз, таблиц и пользователей, разбирает [[Определение данных (DDL)|SQL]], строит план
> - **Хранилище** отвечает только за чтение и запись данных на диск
>
> Между ними — намеренно простой API, чтобы хранилище было легко подменить. Отсюда главный конфликт: **простой API против эффективного выполнения запроса** — планировщик почти ничего не знает о том, как движок физически разложил данные

В отличие от PostgreSQL, где хранилище одно и сросшееся с ядром, в MySQL под каждую таблицу можно выбрать **свой движок** (`ENGINE=InnoDB`). Это и сила (специализация под нагрузку), и источник почти всех подводных камней лекции

## Основные движки
### InnoDB [00:07:01](https://www.youtube.com/watch?v=mkI2q6twyc0&t=421s)
> [!success] Дефолтный движок, единственный с транзакциями
> - [[Транзакции и ACID|транзакции]] и журнал, [[MVCC]]-подобная многоверсионность
> - блокировки на уровне **строки** (а не таблицы) → возможны взаимоблокировки
> - **кластерный индекс**: строки физически лежат в порядке первичного ключа
> - честные [[Целостность и ограничения|внешние ключи]]
>
> Для чего угодно с транзакциями и конкурентной записью (обработка заказов) берут InnoDB

### MyISAM [00:04:22](https://www.youtube.com/watch?v=mkI2q6twyc0&t=262s)
> [!warning] Быстрый на чтении, но без транзакций
> - **нет транзакций** и нет внешних ключей
> - блокировка на уровне **всей таблицы** → плохо под конкурентной записью
> - отдельный кэш индексов, [[Полнотекстовый поиск|полнотекстовый индекс]], отложенная запись ключей (`DELAY_KEY_WRITE`)
> - при сбое таблица бьётся → ручной ремонт `CHECK TABLE` / `REPAIR TABLE`
>
> Ниша — почти-только-чтение и аналитика, где не нужна целостность

> [!quote]- "Магия" внешнего ключа на MyISAM — синтаксис без поведения [01:07:45](https://www.youtube.com/watch?v=mkI2q6twyc0&t=4065s)
> Реальная история лектора: коллега в 2001 году создаёт две таблицы со связью `FOREIGN KEY`, удаляет строку-родителя — а дочерние записи остаются на месте, хотя `ON DELETE CASCADE` обязан их снести. Ни ошибки, ни предупреждения
>
> Ответ нашёлся на форуме: в раннем MySQL поверх MyISAM `FOREIGN KEY` разбирался **на уровне синтаксической совместимости** — конструкция объявлялась и проживала запрос, но **не делала ничего**. Иллюстрация политики MySQL: лучше молча проглотить, чем выдать ошибку

### Memory [00:11:31](https://www.youtube.com/watch?v=mkI2q6twyc0&t=691s)
> [!info] Живёт до перезапуска
> - данные держатся в памяти, после рестарта сервера **пропадают** (структура таблицы остаётся)
> - [[Хеш-индекс|хеш-индексы]] из коробки → поиск по равенству за константу
> - `TEXT`/`BLOB`/`VARCHAR` урезаются до `CHAR` фиксированной длины
> - используется внутри сервера для промежуточных таблиц

### Экзотика [00:12:04](https://www.youtube.com/watch?v=mkI2q6twyc0&t=724s)
- **Archive** — пишет на лету сжатые `gzip`-данные; лектор складировал в нём прокси-логи "с чудовищной скоростью" при дорогом интернете
- **`MERGE`** — объединяет несколько одинаковых MyISAM-таблиц в одну логическую
- **`BLACKHOLE` / `NULL`** — принимает данные и выбрасывает (чёрная дыра), полезно для отладки репликации

## Цена подключаемости: дублирование метаданных
> [!danger] Метаданные живут и в ядре, и в хранилище [00:14:45](https://www.youtube.com/watch?v=mkI2q6twyc0&t=885s)
> Список столбцов таблицы знает и движок запросов, и само хранилище — каждый держит свою копию. Эта рассинхронизация по разным слоям тянет за собой:
> - [[Изменение схемы в MySQL|нетранзакционный DDL]] — `ALTER TABLE` не откатывается;
> - слабость [[Планировщик запросов MySQL|планировщика]] — ядро не видит физической раскладки данных;
> - хрупкость [[Репликация в MySQL|репликации]], которая живёт отдельным журналом мимо хранилища.

> [!note]- Рейтинг [[Реляционная модель данных|СУБД]] — почему именно эта пара [00:00:32](https://www.youtube.com/watch?v=mkI2q6twyc0&t=32s)
> По [db-engines.com](https://db-engines.com/en/ranking) верх рейтинга популярности годами держат Oracle, MySQL, SQL Server, PostgreSQL, MongoDB. MySQL и PostgreSQL — две самые ходовые бесплатные реляционные СУБД, поэтому выбор между ними встаёт на практике постоянно
