# Планировщик запросов MySQL
> [!warning] Планировщик MySQL знает о данных мало и соединяет таблицы единственным способом [00:38:55](https://www.youtube.com/watch?v=mkI2q6twyc0&t=2335s)
> Из-за слабого [[Программный интерфейс приложения|API]] к [[Архитектура MySQL и движки хранения|хранилищу]] оптимизатор почти не видит, как физически разложены данные. Практические последствия — ниже

## Только nested loop
MySQL умеет соединять таблицы лишь [[Стратегии соединения таблиц|вложенным циклом (nested loop)]] — ни merge join, ни hash join. На больших таблицах без подходящего индекса это и есть та разница "3 минуты против 7.7 секунды" из лекции про индексы

Каскадные изменения от [[Триггеры|триггеров]] планировщик при оценке плана тоже **не учитывает** — строит план так, будто триггеров нет

## Предикат не пробрасывается внутрь подзапроса [00:42:27](https://www.youtube.com/watch?v=mkI2q6twyc0&t=2547s)
> [!danger] Представления в MySQL почти бесполезны
> Если выборка идёт из [[Представления (VIEW)|представления]] или подзапроса, MySQL **не проталкивает** внешнее условие фильтра внутрь — материализует подзапрос целиком, а уже потом фильтрует. Нетривиальное представление почти всегда выполняется полностью:
> ```sql
> SELECT * FROM (
>     SELECT title, MIN(description) AS descr
>     FROM film
>     GROUP BY title
> ) f
> WHERE f.title LIKE 'al%';     -- LIKE применится ПОСЛЕ полной группировки всей film
> ```
> В [[Оптимизатор запросов|PostgreSQL]] такой predicate pushdown работает: условие уезжает внутрь, и группируется только нужный кусок

## Заведомо плохие запросы [00:42:54](https://www.youtube.com/watch?v=mkI2q6twyc0&t=2574s)
> [!example] `UNION ALL` + `ORDER BY` поверх
> ```sql
> SELECT title, description FROM foo
> UNION ALL
> SELECT title, description FROM bar
> ORDER BY title;
> ```
> Сортировка поверх объединения заставляет MySQL 5.6 сначала материализовать весь `UNION`, а потом отсортировать целиком — даже если из каждой таблицы есть индекс по `title`, для отсортированного слияния он не используется
