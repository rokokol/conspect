# Определение данных (DDL)
**SQL** (Structured Query Language) делится на два подъязыка: **DDL (Data Definition Language)** меняет *структуру* — `CREATE`/`ALTER`/`DROP TABLE`, а [[Модификация данных (DML)|DML]] меняет *данные* — `SELECT`/`INSERT`/`UPDATE`/`DELETE`. Эта заметка — про DDL

## CREATE TABLE [38:01](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=2281s)
```sql
CREATE TABLE films (
    code      char(5)     CONSTRAINT films_pkey PRIMARY KEY,
    title     varchar(40) NOT NULL,
    date_prod date,                               -- nullable по умолчанию
    kind      varchar(10),
    len       interval hour to minute,
    imdb_id   varchar(20),
    CONSTRAINT films_imdb_key UNIQUE (imdb_id)
);
```
Тип столбца задаёт его [[Реляционная модель данных|домен]]: `char`/`varchar`, `date`/`interval`/`timestamp`, целые разной ширины и т.д. Без явного `NOT NULL` столбец **nullable**

> [!note] Полезные модификаторы CREATE TABLE [38:38](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=2318s)
> - **`IF NOT EXISTS`** — создать, только если таблицы ещё нет. Опора [[Версионирование схемы БД|идемпотентных миграций]] одним мегаскриптом
> - **`TEMPORARY`** — временная таблица: видна только своей сессии и **исчезает при отключении** от [[Реляционная модель данных|СУБД]]. Для "положить-забрать" промежуточные данные
> - **`UNLOGGED`** — таблица без журналирования (быстрее, но не переживёт сбой)
> - **`LIKE другая_таблица` / наследование** — создать по образу другой; в Postgres наследование на практике идёт под **партиционирование**

## Объявление ограничений в DDL [41:05](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=2465s)
Семантика [[Целостность и ограничения|ограничений целостности]] разобрана отдельно; здесь — как они пишутся и DDL-нюансы:

| Ограничение                  | Уровень | DDL-деталь                                               |
| ---------------------------- | ------- | -------------------------------------------------------- |
| `NOT NULL` / `NULL`          | поле    | по умолчанию nullable                                    |
| `DEFAULT выражение`          | поле    | значение при отсутствии явного (см. ниже)                |
| `CHECK (выражение)`          | кортеж  | выражение должно быть истинно в момент вставки           |
| `UNIQUE`                     | таблица | второго такого значения быть не может                    |
| `PRIMARY KEY`                | таблица | один на таблицу; используется в индексах и `FOREIGN KEY` |
| `REFERENCES` (`FOREIGN KEY`) | [[Реляционная модель данных\|БД]]      | ссылка на строку другой таблицы того же типа             |

> [!tip] DEFAULT вычисляется в момент вставки, а не создания таблицы [54:47](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=3287s)
> `DEFAULT nextval('serial')` не берёт число лишь один раз при `CREATE TABLE` сразу для всех кортежей — выражение пересчитывается **на каждую вставляемую строку**, поэтому автоинкремент и выдаёт разные id, а не один и тот же

> [!warning] UNIQUE и NULL: null никогда не равен null [53:42](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=3222s)
> Уникальный столбец допускает **сколько угодно** строк со значением `NULL` (именно `NULL`, не пустая строка): раз `null ≠ null`, дубликатом они не считаются. А вот два одинаковых **не-null** значения уже не вставить

### Внешний ключ: MATCH, DEFERRABLE, действия [45:44](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=2744s)
> [!note]- Тонкости объявления REFERENCES
> - **`MATCH`** для составного внешнего ключа: `MATCH FULL` — либо все столбцы ссылки заданы, либо все `NULL`; `MATCH SIMPLE` (по умолчанию) — допускает, что часть столбцов `NULL`; `MATCH PARTIAL` не поддерживается
> - **`DEFERRABLE INITIALLY DEFERRED`** — разрешает [[Целостность и ограничения|отложить проверку]] на конец транзакции (можно добавить детей раньше родителей). По умолчанию `IMMEDIATE` — проверка сразу
> - Столбец-ссылка должен быть **того же типа**, что и столбец, на который ссылается

> [!important] Полный список действий ON DELETE / ON UPDATE [50:05](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=3005s)
> Что делать с дочерней строкой, когда удаляют/меняют родителя:
>
> | Действие | Поведение |
> |---|---|
> | `NO ACTION` | запрет; проверку **можно отложить** до конца транзакции |
> | `RESTRICT` | то же, но **нельзя отложить** — падает в момент операции |
> | `CASCADE` | удалить/обновить и дочерние строки следом |
> | `SET NULL` | обнулить ссылку в дочерней строке (сделать "сиротой") |
> | `SET DEFAULT` | записать в ссылку значение по умолчанию (родитель с ним должен существовать) |
>
> Разница `NO ACTION` и `RESTRICT` видна только в отложенной транзакции: при `NO ACTION` можно удалить родителя и детей разными операциями и закоммитить (на момент коммита детей уже нет), `RESTRICT` откатит сразу на удалении родителя

> [!tip] Именуй ограничения явно [55:30](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=3330s)
> Безымянный constraint получает автоген-имя, и две структурно одинаковые базы с разной историей миграций получат **разные** авто-имена. Когда понадобится `DROP CONSTRAINT`, имя придётся сначала выяснять обходными путями. Поэтому `FOREIGN KEY`, `UNIQUE` и индексные ограничения называют сразу

> [!info] Postgres не создаёт индекс под FOREIGN KEY [57:23](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=3443s)
> Проверка "есть ли родитель с id 42" без [[Индекс B-tree|индекса]] требует прочитать всю таблицу (индекс — как предметный указатель книги). MySQL заводит индекс под внешний ключ автоматически, **Postgres — нет**, его создают отдельно

## ALTER TABLE — менять структуру [58:52](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=3532s)
`ALTER TABLE` правит **структуру**, не содержимое: переименовать/добавить/удалить столбцы и ограничения.

> [!important] Цена изменения зависит от того, надо ли переписывать данные [59:46](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=3586s)
> На таблице в 20 ГБ:
> - **Добавить nullable-столбец без DEFAULT** — почти мгновенно: `NULL` в данных не хранится, меняются лишь **метаданные**
> - **Добавить `NOT NULL` с `DEFAULT`** — надо вписать значение в каждую строку → **перезапись всех 20 ГБ**
> - **`DROP COLUMN`** — мгновенно (метаданные), но место освобождается **лениво**, по мере перезаписи строк; таблица сразу не "худеет"
>
> Чудес не бывает — операции с [[Стоимость операций|перезаписью диска]] кратно дороже правки метаданных
>
> > [!info]- В MySQL даже добавление столбца — перелив всей таблицы
> > То, что PostgreSQL делает правкой одних метаданных, [[Изменение схемы в MySQL|MySQL на старых версиях выполняет пересборкой таблицы целиком]] — часы блокировки и двойной объём на диске (часть операций обходится флагом `ALGORITHM=INPLACE` с 5.7.4)

> [!tip] Группируй изменения через запятую [1:02:55](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=3775s)
> Два отдельных `ALTER TABLE` с перезаписью пройдут по таблице **дважды**. Перечисленные через запятую в одном `ALTER TABLE` — выполнятся **конвейером**, за один проход

> [!example]- Смена типа с пересчётом — `USING` [1:05:21](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=3921s)
> `int32 → int64` проходит само. А вот "секунды от эпохи → `timestamp with time zone`" штатного каста не имеет. Вместо машинерии "добавить столбец → `UPDATE` → удалить старый" в Postgres есть `USING`:
> ```sql
> ALTER TABLE events
>   ALTER COLUMN ts TYPE timestamp with time zone
>   USING to_timestamp(ts_epoch);
> ```
> Значение нового столбца считается из старого по выражению. Цепочку `USING` можно тянуть длинной, используя столбец как временную переменную внутри одного `ALTER TABLE`
