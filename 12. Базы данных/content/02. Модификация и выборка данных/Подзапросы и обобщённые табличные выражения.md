# Подзапросы и обобщённые табличные выражения
**Подзапрос** — вложенный `SELECT`, результат которого используют как таблицу. **`WITH`** (обобщённое табличное выражение, CTE) даёт подзапросу имя — и, в отличие от обычного подзапроса, умеет **рекурсию**: обойти дерево на **произвольную глубину**, чего обычным [[Соединения JOIN|JOIN]] не сделать (он достаёт лишь фиксированное число уровней)

## Подзапрос в FROM — обязателен алиас [1:44:42](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=6282s)
Подзапрос — это `SELECT` в скобках, поставленный на место таблицы. В [[Выборка данных (SELECT)#FROM — откуда берём строки [1 20 10](https //www.youtube.com/watch?v=dGwkG2VyDTY&t=4810s)|FROM]] его обязательно снабдить **алиасом**, иначе на него не сослаться:
```sql
SELECT a.region, a.total
FROM (
    SELECT region, SUM(amount) AS total
    FROM sales
    GROUP BY region
) a
WHERE a.total > 1000;
```
Алиас обязателен, даже когда подзапрос один и имя по сути не нужно — этого требует синтаксис скобочного запроса. При двух таблицах без алиасов их вообще не различить.

## WITH — именованные подзапросы [2:02:09](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=7329s)
`WITH name AS (…)` объявляет именованный запрос **до** `SELECT` и позволяет ссылаться на него по имени. Применений два: вынести повторяющуюся или громоздкую часть ради читаемости — и рекурсия.

> [!note] Чем CTE отличается от обычного подзапроса [2:02:48](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=7368s)
> - **Умеет не только `SELECT`** — внутри `WITH` допустимы `INSERT`/`UPDATE`/`DELETE` (в подзапросе — только выборка); часто с [[Модификация данных (DML)|`RETURNING`]], чтобы передать изменённые строки дальше
> - **Отдельная сущность для оптимизатора** — `WITH` и основной `SELECT` он обрабатывает порознь, не анализируя запрос целиком

> [!warning] CTE может незаметно убить производительность [2:03:18](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=7398s)
> Раз [[Оптимизатор запросов|оптимизатор]] не заглядывает внутрь CTE, он не протолкнёт в него фильтры и не использует [[Индекс B-tree|индекс]] так, как сделал бы с обычным подзапросом. Пытаясь всего лишь повысить читаемость, легко просесть по скорости "на ровном месте"

```sql
WITH region_sales AS (
    SELECT region, SUM(amount) AS total
    FROM sales
    GROUP BY region
),
top_regions AS (
    SELECT region FROM region_sales
    WHERE total > (SELECT SUM(total) FROM region_sales) * 0.1
)
SELECT region FROM top_regions;  -- регионы с долей продаж выше 10%
```

## Рекурсивные запросы — WITH RECURSIVE [2:04:30](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=7470s)
Изначально в [[Определение данных (DDL)|SQL]] были большие проблемы с обходом дерева: один уровень или фиксированное число уровней через `JOIN` достаётся легко, а уйти на **произвольную глубину** было нельзя. Потом в стандарт ввели рекурсивные подзапросы — поддерживают их по-прежнему не все [[Реляционная модель данных|СУБД]]:
```sql
WITH RECURSIVE rt AS (
        -- якорь: строки без родителя, нулевой уровень
        SELECT id, parent_id, 0 AS level, name
        FROM tree
        WHERE parent_id IS NULL
    UNION ALL
        -- рекурсивная часть: цепляемся к предыдущему шагу
        SELECT t.id, t.parent_id, rt.level + 1, t.name
        FROM tree t
        JOIN rt ON t.parent_id = rt.id
)
SELECT * FROM rt;
```

> [!note] Из чего собран рекурсивный запрос
> - **Якорь** — нулевое состояние, с чего начинается обход (корни: строки без родителя, `level = 0`)
> - **`UNION ALL`** здесь — **не** объединение в обычном смысле, а специальный разделитель: "дальше идёт рекурсивная часть". Поэтому, в отличие от классического [[Выборка данных (SELECT)|`UNION`]], **части нельзя менять местами** — сначала якорь, потом рекурсия
> - **Рекурсивная часть** — `JOIN` к результату **предыдущего** шага (`rt`): `id` текущих строк уже стал родителем для следующих, уровень растёт на единицу
> - **Алиас обязателен**: поле `id` есть и в `tree`, и в `rt` — без алиаса непонятно, откуда его брать

> [!warning] Рекурсия гарантирует обход, но не порядок строк [2:08:16](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=7696s)
> Нам обещали рекурсивный обход — обещание сдержано; но про **порядок** вывода речи не было. В разборе "Бутово" оказалось выведено под "Вашингтоном" хотя относится к "Москве": уровень вложенности посчитан верно, а взаимный порядок строк произволен. Единственное полезное, что даёт голый обход, — номер уровня

> [!tip] Трюк: накапливать путь и получить материализованный путь [2:08:42](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=7722s)
> Чтобы вытащить больше, чем уровень, в рекурсии **собирают путь** — массив `id` от корня: якорь кладёт `path = {id}`, рекурсивная часть дописывает к нему `id` текущей строки. На выходе — [[Иерархические структуры в БД#Материализованный путь — путь в строке [2 32 38](https //www.youtube.com/watch?v=dGwkG2VyDTY&t=9158s)|материализованный путь]] до каждой записи, по которому уже видно и предков, и порядок
