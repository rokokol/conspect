# Соединения JOIN
**JOIN** соединяет две таблицы по условию (обычно "внешний ключ дочерней = ключ родителя") — это [[Реляционная алгебра|соединение из реляционной алгебры]]: декартово произведение плюс фильтр. Вид JOIN определяет, что делать со строками, которым **не нашлось пары**

## Виды соединений [1:25:40](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=5140s)
![[Виды JOIN.png]]

| Вид | Что в результате |
|---|---|
| **`INNER JOIN`** | только строки, у которых пара нашлась в **обеих** таблицах (пересечение) |
| **`LEFT JOIN`** | все строки левой таблицы; где пары в правой нет — на её месте `NULL` |
| **`RIGHT JOIN`** | симметрично left: все строки правой, недостающее слева — `NULL` |
| **`FULL JOIN`** | все строки обеих таблиц вне зависимости от наличия пары |
| **`CROSS JOIN`** | [[Реляционная алгебра\|декартово произведение]] — каждая строка A с каждой строкой B, без условия |

```sql
SELECT * FROM cartoons c JOIN channels ch ON c.channel_id = ch.id;  -- inner
SELECT * FROM cartoons c LEFT JOIN channels ch ON c.channel_id = ch.id;
```

> [!note] Что подразумевается без модификатора [1:28:46](https://www.youtube.com/watch?v=dGwkG2VyDTY&t=5326s)
> - Голый `JOIN` — это `INNER JOIN`
> - Две таблицы через запятую в `FROM` **без условия** — `CROSS JOIN` (полное перемножение): для каждой строки A целиком повторяется таблица B
>
> `LEFT`/`RIGHT` — это `INNER`, дополненный непарными строками соответствующей стороны

## Задание условия: ON, USING, NATURAL
Условие соединения пишут тремя способами:

| Способ | Условие | Дубль общего столбца |
|---|---|---|
| `JOIN … ON a.id = b.a_id` | произвольное, явно | оба столбца в выводе |
| `JOIN … USING (id)` | равенство по **явному** списку столбцов | столбец выводится **один раз** |
| `NATURAL JOIN` | равенство по **всем** одноимённым столбцам | столбец выводится один раз |

### NATURAL JOIN — удобно, но опасно [40:39](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=2439s)
`NATURAL JOIN` соединяет по **всем** столбцам, чьи имена и типы совпадают в обеих таблицах (порядок столбцов неважен — важны имена и типы)

> [!danger] Новый столбец молча ломает условие [42:44](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=2564s)
> Добавили в таблицу столбец, имя которого случайно совпало со столбцом другой таблицы — и условие `NATURAL JOIN` **изменилось само собой**, запрос стал считать другое. Поэтому лектор не рекомендует `NATURAL JOIN`, а советует `JOIN USING` (или `JOIN ON`): там список столбцов задан **явно**, и добавление/удаление колонок поведение запроса кардинально не меняет

```sql
-- предпочтительно: явный список столбцов соединения
SELECT * FROM employees e JOIN departments d USING (department_id);
```

> [!tip] Индекс по полям соединения нужен [41:03](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=2463s)
> На столбцы, по которым идёт `JOIN`, индекс **крайне желателен** — от него зависит стратегия и скорость соединения. Исключение — экзотика с тремя строками в таблице; на "разумном, ненулевом" объёме индекс обязателен. Детали — на занятии про [[Оптимизатор запросов|оптимизацию запросов]]

## Self-join — таблица соединяется с собой [27:13](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=1633s)
Одну таблицу можно соединить **саму с собой**, дав ей два разных алиаса — типичный приём для иерархий и отношений "строка ↔ строка"

> [!example] Школьники, дружащие только в своём классе [1:27:13](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=5233s)
> Таблицы: `highschooler (id, name, grade)` и `friend (id1, id2)` (дружба симметрична — на пару `1↔2` есть и обратная запись). Нужны школьники, у которых **есть** друзья, но **нет** друзей из другого класса
>
> Идея: соединяем школьника с его друзьями, а друзей — со школьниками **другого** класса. Если такого "друга из чужого класса" не нашлось (`LEFT JOIN` дал `NULL`) — школьник подходит. Это **антисоединение** через `LEFT JOIN … IS NULL`:
> ```sql
> SELECT DISTINCT h.name, h.grade
> FROM highschooler h
> JOIN friend f       ON f.id1 = h.id                 -- у школьника есть друг
> LEFT JOIN highschooler o
>        ON o.id = f.id2 AND o.grade <> h.grade        -- друг из ДРУГОГО класса
> WHERE o.id IS NULL;                                  -- такого друга нет
> ```
> `highschooler` тут участвует **дважды** (`h` — сам школьник, `o` — друг из другого класса) — это и есть self-join

## FULL JOIN = LEFT ∪ RIGHT-antijoin [53:04](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=3184s)
`FULL JOIN` внутри раскладывается в `LEFT JOIN` плюс "хвост" правой таблицы — строки, которым **не нашлось пары слева**
```sql
SELECT e.name, d.department_name
FROM employees e LEFT JOIN departments d ON e.dept_id = d.id
UNION ALL
SELECT NULL, d.department_name
FROM departments d
WHERE NOT EXISTS (SELECT 1 FROM employees e WHERE e.dept_id = d.id);
```

> [!warning] UNION ALL vs UNION тут не одно и то же
> Через `UNION ALL` склейка точна, потому что левый запрос уже даёт все строки с парой, а нижний добавляет только **непарные** справа. Если в данных есть полные дубликаты строк (два одинаковых сотрудника одного возраста в одном отделе), `UNION ALL` их сохранит, а `UNION` (с дедупликацией) — **съест** один из них, и запросы перестанут быть эквивалентны
