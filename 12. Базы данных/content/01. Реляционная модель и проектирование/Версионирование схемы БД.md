# Версионирование схемы БД
> [!note] Перевод базы со старой версии схемы на новую называется **миграцией**
> Причем, это применяется не только для обновления версии [[Реляционная модель данных|БД]], но еще и при переносе данных из одной БД в другую. Например, переносе данных о клиентах из ресторана в банк

Приложение развивается, и его схема меняется — добавляются столбцы и таблицы. Главная боль здесь — **сохранить данные**: вариант "удалить всё и создать с нуля" не годится, потому что в базе лежит то, чего в новой версии кода уже нет, а выкинуть просто так нельзя

> [!important] Код можно заменить, данные — нужно мигрировать [1:32:14](https://www.youtube.com/watch?v=SfYaAQ9-RnE&t=5534s)
> Логику обновляют легко: старый алгоритм выкинул, новый вставил — "боты раньше упирались в стену, теперь обходят". С **данными так нельзя**: если завели новый столбец "когда игрок последний раз заходил", у старых записей этого значения нет — и нужно решить, чем его заполнить. Состояние, которое было раньше, приходится учитывать всегда

## Чего хотим от системы миграций [1:33:43](https://www.youtube.com/watch?v=SfYaAQ9-RnE&t=5623s)
> [!note] Требования к удачной схеме миграций
> - **Обновление до любой версии** — поднять базу с произвольной старой версии до свежей одним заходом, не прогоняя руками 1.7 → 1.8 → 1.9 → …
> - **Простота написания** самой миграции — чем меньше ручных мест, тем лучше
> - **Создание базы с нуля** — должно быть тривиально
> - **Параллельные ветки** — разработка в нескольких ветках не должна ломать нумерацию
> - **Откат** — желательна возможность вернуться, если обновление не удалось

## Три способа версионирования схемы [1:35:00](https://www.youtube.com/watch?v=SfYaAQ9-RnE&t=5700s)
### Генерация из исходного кода
Схему описывают в коде, а скрипт перехода между версиями **генерирует инструмент**: есть старое описание, есть новое — разницу он выведет сам

- ✅ Изменения структуры удобно видеть в системе контроля версий; база создаётся с нуля из одного описания; ручного вмешательства почти нет
- ❌ Генератор знает, *что* поменялось, но не знает, **зачем** — и потому не умеет мигрировать **смысл данных**. Если флажок "есть меч" превратился в число "сколько мечей", автомат не догадается, как пересчитать одно в другое; такие преобразования всё равно пишут руками

> [!tip] Где "только добавляем" — генерация идеальна
> Если схема только растёт (историческая база, куда сваливаются события: 500 таблиц, новые столбцы добавляются, старые не трогают), генерация по описанию "что хотим получить" работает безупречно — сравнили желаемые столбцы с имеющимися, недостающие досоздали. Старые данные не удаляют: что с ними делать — всё равно непонятно, а места они просят немного

### Инкрементные изменения [1:39:35](https://www.youtube.com/watch?v=SfYaAQ9-RnE&t=5975s)
Каждое изменение — отдельный **пронумерованный патч-файл**; миграция накатывает недостающие по очереди:
```
Database/
├─ Baseline.sql      ← база с нуля
├─ 0001.03.01.sql
├─ 0002.03.01.sql
├─ 0003.03.01.sql
└─ 0004.03.02.sql
```
Версию хранит сама база — служебная таблица истории миграций:
```sql
CREATE TABLE migration_history (
    id            INT AUTO_INCREMENT PRIMARY KEY,
    major_version VARCHAR(2),
    minor_version VARCHAR(2),
    file_number   VARCHAR(4),
    description   VARCHAR(255),
    date_applied  TIMESTAMP
);
```
При старте сервер смотрит, какие патчи уже применены, и докатывает остальные по порядку. Заодно проверяет, **нет ли лишних** патчей — это признак, что на свежую базу запускают старый сервер (без явного флага такой запуск останавливают).

- ✅ Быстрая миграция до свежей версии; номер версии лежит в самой базе
- ❌ Параллельная разработка в нескольких ветках конфликтует по нумерации; нужен инструмент-накатчик
- Откат отдельно не генерируется: либо к каждому патчу пишут **обратный** скрипт, либо откат не поддерживают вовсе

### Идемпотентные изменения
Один файл `Changes.sql` на версию пишут так, чтобы его можно было выполнить **из любого промежуточного состояния** — каждый шаг защищён проверкой существования:
```sql
IF NOT EXISTS (
    SELECT *
    FROM information_schema.tables
    WHERE table_name = 'my_table'
      AND table_schema = 'my_db'
)
THEN
    CREATE TABLE my_table (
        id       INT(10)      NOT NULL,
        my_field VARCHAR(255) NULL,
        PRIMARY KEY (id)
    );
END IF;
```

- ✅ Прогнал `Changes.sql` — и база приходит к нужной версии откуда угодно, повторный запуск ничего не ломает
- ❌ Идемпотентность стоит лишнего кода (обёртки `IF NOT EXISTS`); при неаккуратной правке легко потерять данные
