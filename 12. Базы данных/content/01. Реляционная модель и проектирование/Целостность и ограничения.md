# Целостность и ограничения
**Ограничения целостности** — это правила корректности данных, которые **человек объявляет декларативно**, а соблюдать заставляет [[Реляционная модель данных|СУБД]]: испортить данные в обход ограничения движок просто не даст. Это второй из [[Реляционная модель данных#Три аспекта модели [25 40](https //www.youtube.com/watch?v=SfYaAQ9-RnE&t=1540s)|трёх аспектов реляционной модели]]

> [!important] Целостность держит СУБД, а не приложение [29:23](https://www.youtube.com/watch?v=SfYaAQ9-RnE&t=1763s)
> Может показаться, что контроль на уровне СУБД лишний — приложение и само проверит данные перед вставкой. Но часть условий приложению проверить тяжело: что у человека есть имя — легко, а вот **уникальность** имени по всей таблице или **отсутствие висячих ссылок** — уже дорого и гонко (между проверкой и вставкой данные мог поменять другой клиент). Поэтому такие инварианты отдают движку

## Три уровня ограничений [27:52](https://www.youtube.com/watch?v=SfYaAQ9-RnE&t=1672s)
Ограничение действует на одном из трёх уровней — по тому, сколько данных оно охватывает:

| Уровень | Что ограничивает | Пример |
|---|---|---|
| **Домен** | один атрибут, его тип и допустимые значения | возраст — целое $\geqslant 0$; имя — `NOT NULL` |
| **Отношение** | связь атрибутов *внутри* одного кортежа или строк таблицы между собой | премия не больше оклада; `UNIQUE` логина |
| **База данных** | связь между *разными* таблицами | у каждого ребёнка есть родитель — [[Целостность и ограничения#Ссылочная целостность и FOREIGN KEY [1 21 31](https //www.youtube.com/watch?v=SfYaAQ9-RnE&t=4891s)\|внешний ключ]] |

## Виды ограничений [1:28:38](https://www.youtube.com/watch?v=SfYaAQ9-RnE&t=5318s)
> [!note] Декларативный арсенал — что движок проверяет сам
> | Ограничение | Гарантирует |
> |---|---|
> | `NOT NULL` | значение атрибута присутствует |
> | `UNIQUE` | нет двух строк с одинаковым значением (через уникальный [[Индекс B-tree\|индекс]]) |
> | `PRIMARY KEY` | `NOT NULL` + `UNIQUE` для [[Ключи отношения\|первичного ключа]] |
> | `CHECK (выражение)` | строку добавляют, только если выражение истинно |
> | `FOREIGN KEY` | значение ссылается на существующую строку родительской таблицы |
>
> Шестой способ — [[Триггеры\|триггеры]], но это уже **императивный** механизм, стоящий особняком (см. ниже)

## Ссылочная целостность и FOREIGN KEY [1:21:31](https://www.youtube.com/watch?v=SfYaAQ9-RnE&t=4891s)
**Внешний ключ (`FOREIGN KEY`)** объявляет: значение атрибута обязано совпадать с [[Ключи отношения\|первичным ключом]] строки в другой таблице. Движок начинает требовать это соответствие — нельзя завести регион, ссылающийся на несуществующую страну:
```sql
CREATE TABLE country (
  id        bigserial    NOT NULL PRIMARY KEY,
  name      varchar(128) NOT NULL
);

CREATE TABLE region (
  id         bigserial    NOT NULL PRIMARY KEY,
  country_id bigint       NOT NULL,
  name       varchar(128) NOT NULL,
  FOREIGN KEY (country_id) REFERENCES country (id)
);

CREATE TABLE city (
  id        bigserial    NOT NULL PRIMARY KEY,
  region_id bigint       NOT NULL,
  name      varchar(128) NOT NULL,
  FOREIGN KEY (region_id) REFERENCES region (id)
);
```

> [!tip] Порядок вставки можно нарушить внутри транзакции [1:22:06](https://www.youtube.com/watch?v=SfYaAQ9-RnE&t=4926s)
> По умолчанию `FOREIGN KEY` запрещает вставить дочернюю строку раньше родителя. Но проверку можно отложить **на конец [[Транзакции и ACID\|транзакции]]**: внутри неё строки добавляют в любом порядке (страна, регион, город или наоборот), а согласованность движок проверяет один раз — при коммите. Внешний наблюдатель промежуточного несогласованного состояния не видит

### ON DELETE — каскад или запрет [1:22:48](https://www.youtube.com/watch?v=SfYaAQ9-RnE&t=4968s)
Удаление родителя, на которого ссылаются дети, движок разруливает по правилу внешнего ключа:

- **Запрет (по умолчанию)** — удалить страну, пока на неё ссылается регион, нельзя; СУБД вернёт ошибку
- **Каскад (`ON DELETE CASCADE`)** — удаление родителя тянет за собой все дочерние строки (страна → регионы → города). Удалиться может сколь угодно много записей

> [!example] Каскад встречает запрет внутри транзакции [1:25:38](https://www.youtube.com/watch?v=SfYaAQ9-RnE&t=5138s)
> Пусть `region.country_id` — **каскадный**, а `city.region_id` — **запрет**. Удаляем страну:
> 1. в транзакции каскад удаляет её регионы;
> 2. каждый регион пытается утянуть свои города — а там запрет;
> 3. возникает ошибка "нельзя удалить регион, на него ссылаются города";
> 4. **вся транзакция откатывается** — база возвращается в состояние до её начала
>
> Итог: операция атомарна, частично "полуудалённого" состояния не остаётся. База не позволяет себе сломать ссылочную целостность даже на промежуточном шаге

## Декларативно против императивно: триггеры [1:23:59](https://www.youtube.com/watch?v=SfYaAQ9-RnE&t=5039s)
`FOREIGN KEY`/`CHECK` **декларативны** — человек описывает *что* должно быть истинно, а *как* это проверить, решает движок. Альтернатива — [[Триггеры\|триггер]]: процедура, срабатывающая на событие (`INSERT`/`DELETE`/…) и **императивно** делающая что угодно: записать в журнал "удалено столько-то строк", проверить права пользователя на удаление, перенести данные. Гибче, но и ответственность за корректность переходит на автора триггера

> [!info] Ограничение можно навесить и постфактум
> `FOREIGN KEY` добавляют на уже заполненную таблицу — но движок сперва проверит, что **текущие** данные ему удовлетворяют. Есть хоть один регион без страны — `ALTER TABLE` упадёт с ошибкой; пройдёт — и с этого момента регион без страны уже не вставить
