# Регистронезависимый поиск
Регистронезависимого сравнения **из коробки в PostgreSQL нет** (в отличие от [[COLLATION и регистронезависимое сравнение|MySQL, где его даёт collation с суффиксом `_ci`]]) — collation отвечает только за сортировку. Поиск без учёта регистра делают тремя путями: функциональный индекс по `lower()`, тип `citext` или (для сравнения по правилам языка) [[COLLATION и регистронезависимое сравнение|ICU]]-коллации

## Collation — правило сравнения строк [01:18](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=78s)
**Collation** (коллация) — правило сравнения и сортировки строк, зависящее от **локали**. Без него строки сортируются по кодам символов: сначала знаки препинания, потом большие латинские буквы, потом маленькие, и только в конце — кириллица. Локаль (`en_US.utf8`, `ru_RU.utf8`, `ucs_basic`) задаёт человеческий порядок: регистр и язык учитываются

> [!warning] Локаль ломает переносимость [[Реляционная модель данных|БД]] [02:43](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=163s)
> Правила локали берутся **из операционной системы**, и под Linux и Windows они **разные**. База с уникальным индексом по текстовому полю, годами работавшая под Linux, под Windows может **не развернуться**: другой порядок сортировки → другая трактовка уникальности → конфликт ключей на тех же данных

### Турецкая I — регистр зависит от языка [06:30](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=390s)
Преобразование верхний ↔ нижний регистр **не универсально**. Классическая ловушка — турецкая `i`: в турецкой локали `I` и `i` — разные буквы (есть `İ`/`ı` с точкой и без), поэтому `upper('i')` и `lower('I')` дают не то, что в английской. Если БД международного продукта живёт на английской локали как "самой нейтральной", турецкие пользователи получают неожиданные результаты

> [!info] Турецкая локаль однажды положила сборку Ubuntu [08:45](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=525s)
> Из-за этого преобразования регистра пакет когда-то не собирался под турецкой локалью — пришлось специально добавлять обходной путь

## Функциональный индекс по lower() [10:26](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=626s)
Самый распространённый и давний подход: уникальный индекс не по самому полю, а по **функции** `lower(name)`. Строка приводится к нижнему регистру и в таком виде попадает в индекс — две строки, совпавшие в нижнем регистре, в уникальный индекс уже не лягут
```sql
CREATE UNIQUE INDEX users_name_lower_idx ON users (lower(name));

-- искать тоже надо через lower(), иначе индекс не задействуется:
SELECT * FROM users WHERE lower(name) = lower('Ivan');
```

> [!warning] Цена подхода
> - **Запрос обязан повторять `lower()`** на колонке: голый `WHERE name = …` индекс не использует
> - **Аргумент тоже приводим в БД, а не в приложении** — иначе из-за разных правил регистра на клиенте и сервере получим неожиданные сайд-эффекты
> - `е`/`ё` остаются **разными** буквами, турецкую проблему это тоже не лечит — только регистр

## citext — регистронезависимый тип [13:33](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=813s)
Чтобы не писать `lower()` в каждом запросе, есть расширение **`citext`** (case-insensitive text): отдельный текстовый тип, который сам делает приведение к нижнему регистру при сравнении. Функционально эквивалентно индексу по `lower()`, но пользоваться субъективно удобнее
```sql
CREATE EXTENSION IF NOT EXISTS citext;

CREATE TABLE users (
    id    bigserial PRIMARY KEY,
    email citext UNIQUE          -- сравнение без учёта регистра "бесплатно"
);
```

> [!note] citext не в коробке, но всегда рядом
> Расширение не входит в стандартную поставку, но идёт в составе пакетов PostgreSQL (`postgresql-contrib`) — достаточно один раз выполнить `CREATE EXTENSION`

## Сравнение по правилам языка — ICU
Для честного языкового сравнения (а не просто регистра) PostgreSQL 10+ умеет коллации на базе библиотеки **ICU** — кросс-платформенные правила сортировки, не зависящие от локали [[Операционная система|ОС]]. Это снимает проблему "Linux vs Windows", но `lower()`/`citext` остаются проще там, где нужен именно регистронезависимый поиск
