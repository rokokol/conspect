# Представления (VIEW)
**Представление** (view) — это **именованный `SELECT`**: сохранённый под именем запрос, к которому потом обращаются как к таблице. Своих данных не хранит — при каждом обращении подставляется и выполняется как [[Предикаты подзапросов|подзапрос]]

## Создание [2:02:05](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=7325s)
```sql
CREATE OR REPLACE VIEW active_users AS
SELECT id, name, email FROM users WHERE active;
```

| Опция | Что делает |
|---|---|
| `OR REPLACE` | создать или переопределить, если уже есть |
| `TEMP` | временное; удалится по завершении транзакции (а если view читает из временной таблицы — оно станет временным автоматически) |
| `RECURSIVE` | рекурсивное представление (можно, но лектор "даже думать не хочет") |
| `WITH … CHECK OPTION` | проверять условие view при вставке/обновлении |

## Зачем нужны [2:03:37](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=7417s)
- **Переиспользование сложного запроса** — длинный нетривиальный `SELECT` (у лектора это был запрос на список звонков в кол-центр) пишется один раз и зовётся по имени
- **Развязка [[Реляционная модель данных|БД]] и приложения** — структура таблицы поменялась, но представление продолжает отдавать данные в прежнем виде; команды БД и кода договариваются на уровне view, а не на уровне таблиц
- **Разграничение доступа** [2:05:33](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=7533s) — выдав права на view вместо таблицы, ограничиваем, что пользователь видит и меняет. Например, view с условием `owner = current_user` покажет каждому только **его** строки; на чтение из таблицы он бы видел всё

## Обновляемые представления [2:06:36](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=7596s)
Через **простое** представление можно делать `INSERT`/`UPDATE`/`DELETE` — изменения "проворачиваются в обратную сторону" и применяются к таблице (неуказанные поля получают значения по умолчанию)

> [!warning] Когда view нельзя менять
> Представление **обновляемо**, только если оно простое: **одна таблица**, без `JOIN`, без группировок. Ломают обновляемость:
> - `GROUP BY`, агрегации, `DISTINCT`, `HAVING`, `LIMIT`/`OFFSET`
> - `UNION` и другие операции над множествами, несколько таблиц
> - **вычисляемое поле** — "фарш в обратную сторону провернуть не удастся"
>
> Ещё ограничения: у view **нет своих триггеров** (использует триггеры базовой таблицы), а все таблицы из запроса должны существовать на момент создания. Вычисляемому столбцу или столбцу, совпавшему по имени с другим, имя задают **явно** через `AS`

### WITH CHECK OPTION [2:08:43](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=7723s)
По умолчанию через view можно вставить строку, **не удовлетворяющую** его условию (она просто уйдёт в таблицу и в самом view не будет видна). `WITH CHECK OPTION` это запрещает — вставляемая строка проверяется на условие представления

> [!example] View комедий с проверкой
> ```sql
> CREATE VIEW comedies AS
> SELECT * FROM films WHERE kind = 'Comedy'
> WITH CASCADED CHECK OPTION;
> ```
> `INSERT` комедии пройдёт, а вставка мультфильма (`kind = 'Animation'`) даст **ошибку**: строка не равна условию `kind = 'Comedy'`. Без `CHECK OPTION` мультфильм бы молча добавился в `films`. `CASCADED` проверяет условия и вложенных представлений, `LOCAL` — только этого

## View ведёт себя как подзапрос [2:10:13](https://www.youtube.com/watch?v=nbmEBvoVAp0&t=7813s)
Представление **не материализуется** заранее — на этапе выполнения оно встраивается во внешний запрос как подзапрос, и условия внешнего запроса **проталкиваются внутрь** оптимизатором (predicate pushdown)
```sql
SELECT * FROM comedies WHERE title LIKE 'Zomb%';
```
Здесь `LIKE 'Zomb%'` спускается на уровень `films`, и из таблицы сразу выбираются фильмы с `kind = 'Comedy'` **и** `title LIKE 'Zomb%'` — а не "сначала все комедии, потом из них зомби"
