# Индексы в MongoDB
Индексы в MongoDB — те же [[Индекс B-tree|B-деревья]], что и в реляционных базах, с теми же плюсами и расплатой. Ничего в структуре не изменилось: полный/левый-префикс/диапазон/сортировка, [[Индекс B-tree#Ограничение составного ключа [05 11](https //www.youtube.com/watch?v=4Tgvd6NPufs&t=311s)|составной ключ по левому префиксу]]. Главная причина медленного приложения — **отсутствие нужного индекса**

> [!warning] Без индекса Mongo может просто отказаться работать
> Во 2-й версии, если по условию находилось слишком много документов без индекса, запрос **вообще ничего не возвращал** — "сделайте индекс". А сортировка результата больше **32 МБ** без индекса до сих пор просто не выполняется — Mongo откажется сортировать

## Виды индексов [1:05:28](https://www.youtube.com/watch?v=_I9vLOAsFew&t=3928s)
Создаются `db.collection.createIndex({field: 1})` — атрибут и порядок сортировки (`1`/`-1`):

- **одинарные** и **составные** (compound) — по нескольким полям сразу; можно индексировать вложенное поле через [[Выборка данных (find)#Обращение внутрь документа [41 17](https //www.youtube.com/watch?v=_I9vLOAsFew&t=2477s)|dot notation]] и **массивы** (multikey)
- **уникальные** — гарантируют неповторяемость значения; при построении по неуникальному полю индекс не создастся
- **разреженные** (sparse) — по полю, которого нет во всех документах (обычный по такому не построить); можно сочетать с уникальным

> [!danger] dropDups удаляет документы молча — не используй
> У уникального индекса была опция **dropDups**: при построении она **удаляет** документы с дубликатами. Функция "страшная и непонятно зачем нужна" — что-то без твоего ведома стирает данные из базы. В 99% случаев это не то, что нужно

### Геопространственный индекс [1:12:07](https://www.youtube.com/watch?v=_I9vLOAsFew&t=4327s)
Индекс по координатам (чаще 2D, есть и 3D) функцией `2d`. Даёт модификатор **`$near`** — найти документы, где точка близко к заданной (по умолчанию в некотором радиусе). Полезно для "друг зачекинился рядом" — реляционный аналог [[Географические данные (PostGIS)|PostGIS]]

### Самоудаление по TTL-индексу [1:13:29](https://www.youtube.com/watch?v=_I9vLOAsFew&t=4409s)
Индекс по полю с timestamp, у которого задан срок жизни: документ **сам удалится** через заданное время после появления. Пример — pastebin, где текст хранится один день: поле с моментом вставки + [[TTL]]-индекс на сутки

### Фоновое построение [1:06:53](https://www.youtube.com/watch?v=_I9vLOAsFew&t=4013s)
`createIndex` по умолчанию **блокирующий**. Можно строить в **фоне** (`background`) — дольше, но без блокировки; с версии ~3.2 это возможно и на secondary-узлах. Некоторые вшивают построение индекса прямо в код приложения — тогда сначала проверяй `getIndexes()`, иначе блокирующая операция надолго повесит запуск

## Ограничения индексов [1:14:55](https://www.youtube.com/watch?v=_I9vLOAsFew&t=4495s)
"Минное поле" с теми же недостатками, что везде — память, поддержка, замедление записи из-за перестройки дерева. Плюс специфика:

- **не больше 64 индексов** на коллекцию (упёрся — "где-то в жизни свернул не туда")
- ограничен размер **ключа** и **имени** индекса
- запрос использует **только ОДИН индекс** — Mongo не мержит два индекса (`a` и `b` при `a OR b<3`)
- индексы **не дружат** с регулярными выражениями и отрицаниями (строятся не по отрицанию)
- **низкая селективность** (статус, гендер) — плохой кандидат в индекс

## Покрывающие запросы [1:21:21](https://www.youtube.com/watch?v=_I9vLOAsFew&t=4881s)
Понятие [[Покрывающий индекс|покрывающего запроса]] есть — целиком ответить из индекса. Но полезно **меньше**, чем в реляционных базах: там [[Частичный, функциональный и кластерный индексы|кластерный индекс]] позволяет избежать вторичного просмотра по ключу, а здесь этого выигрыша нет

## Оптимизатор и explain [1:17:16](https://www.youtube.com/watch?v=_I9vLOAsFew&t=4636s)
Какой индекс выбрать — решает [[Оптимизатор запросов|оптимизатор]], молодой и "зелёный". Он строит несколько планов, меряет их внутренними метриками, кэширует и **перепланирует** при повторных запросах, проверяя, остался ли план оптимальным.

Смотреть план — `explain()` (аналог [[EXPLAIN — план выполнения запроса|EXPLAIN]]): число просканированных ключей и документов, миллисекунды, **winning plan**. Есть и [[Профилирование и протоколирование запросов|профайлер]]. Не нравится выбор — можно навязать индекс через `hint()`
