# Слабоструктурированные данные и JSON
Иногда [[Нормальные формы|нормализация]] не нужна: данные хранят одним документом, а не раскладывают по таблицам. Взамен теряются [[Соединения JOIN|JOIN]], но появляется возможность менять структуру без длительного простоя

## Когда не нормализуют [1:29:40](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=5380s)
> [!abstract] Три ситуации
> - **сервер не работает с содержимым** — настройки клиента сервер получает и отдаёт целиком, не ищет и не правит внутри; для него это просто набор байт, раскладывать по таблицам незачем;
> - **вырожденная структура** — схему CAD-чертежа (CAD — Computer-Aided Design) можно положить в нормализованные таблицы, но практического смысла в этом нет;
> - **частая смена структуры** — историческая база событий ("игрок убил моба" с кучей полей) на 500 ГБ: добавить или удалить столбец это `ALTER TABLE` на несколько часов. Документ без схемы меняют иначе — у него своя **версия**, и при чтении старый документ преобразуется к свежему виду уже в рантайме

> [!info] Расплата — нет JOIN
> Без нормализации исчезают связи через внешние ключи: соединять нечего, приходится выкручиваться без [[Соединения JOIN|JOIN]]. Зато [[Изменение схемы без простоя|правка структуры]] не требует долгой профилактики

## Форматы хранения документа [1:35:43](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=5743s)
> [!example]- Бинарный шмат портит данные молча
> Параметры клиента хранились двоичным форматом (Protobuf-подобным). Битый "шмат" приезжал с клиента и ронял его при загрузке. Лечение: валидация на сервере (мусор не сохранять), конвертер-чистильщик по всем записям, а затем замена всего хитрого бинарного формата на **JSON** (JavaScript Object Notation)

| Формат | Плюсы | Минусы |
|---|---|---|
| **Бинарный** (Protobuf, MessagePack) | компактный | непрозрачный "шмат" — не посмотреть, не запросить из [[Реляционная модель данных\|СУБД]] |
| **Текстовый** | читается глазами, доступен `LIKE` и [[Полнотекстовый поиск\|полнотекстовый поиск]] | всё ещё бесструктурный текст |
| **XML** (eXtensible Markup Language) | СУБД индексирует, бегает по тегам, валидирует | многословный |
| **JSON / JSONB** | валидация, индексы, запросы по полям | — |

> [!tip] Зачем структурированный формат (XML/JSON) вместо бинарного
> - **валидация** — объявив поле как JSON, нельзя записать туда синтаксический мусор: СУБД отвергнет некорректное;
> - **индексы** по содержимому документа;
> - **запросы** по отдельным полям документа

## JSON и JSONB [1:40:01](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=6001s)
> [!note] JSONB хранится в бинарном виде
> `JSONB` — это JSON, разобранный и сохранённый в бинарном представлении, что ускоряет операции над ним. Документ собирают функцией `json_build_object`, агрегаты вроде жанров — массивом:
> ```sql
> CREATE TABLE movies_json (id INT PRIMARY KEY, data JSONB);
>
> INSERT INTO movies_json (id, data)
> SELECT m.id, json_build_object(
>     'title',  title,
>     'year',   year,
>     'genres', (SELECT array_to_json(array_agg(g.name))
>                FROM movie_genres mg JOIN genres g ON mg.genre_id = g.id
>                WHERE mg.movie_id = m.id))
> FROM movies m;
> ```

## Операторы JSONB [1:41:45](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=6105s)
| Оператор | Смысл |
|---|---|
| `A @> B` / `B <@ A` | `B` — подмножество `A` (все ключи и значения `B` есть в `A`) |
| `A ?\| array[...]` | есть **хоть один** из ключей/значений (верхний уровень) |
| `A ?& array[...]` | есть **все** перечисленные ключи/значения |
| `A -> B` | элемент по ключу `B` как **объект** (можно мучить дальше) |
| `A ->> B` | элемент по ключу `B` как **текст** |
| `A #> '{B,C}'` / `A #>> '{B,C}'` | элемент по **пути** (объект / текст) |

## Индексы по JSON [1:44:25](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=6265s)
Два способа найти фильм по названию дают одинаковый результат, но индексируются по-разному:

> [!success] Containment `@>` под [[Специализированные индексы (GiST, GIN, битовый)|GIN]]-индексом
> ```sql
> CREATE INDEX idx_movies_data ON movies_json USING GIN (data);
> SELECT data FROM movies_json WHERE data @> '{"title": "Zombieland"}';
> ```
> [[Специализированные индексы (GiST, GIN, битовый)|GIN]] индексирует **весь документ** (ключи и значения) — универсален, но крупный

> [!success] Равенство по полю под функциональным индексом
> ```sql
> CREATE INDEX idx_movies_title ON movies_json ((data->>'title'));
> SELECT data FROM movies_json WHERE data->>'title' = 'Zombieland';
> ```
> [[Частичный, функциональный и кластерный индексы|Функциональный индекс]] по одному полю компактнее и быстрее, но работает **только** под свой запрос. Для `LIKE` строят функциональный индекс по тому же выражению

> [!warning] Поиск по вложенным полям индексируется частично [1:46:30](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=6390s)
> ```sql
> SELECT data->>'title' FROM movies_json
> WHERE data @> '{"genres": ["Comedy"], "tags": ["zombie"]}';
> ```
> Строгое вхождение `@>` через GIN индексируется, а вот `LIKE` по вложенным полям ускорить почти нечем[^vodka]

[^vodka]: На момент лекции анонсировали оператор `@@` для поиска по JSON (с `>`/`<` и масками, как в полнотекстовом поиске) и индекс под него с гордым именем **VODKA** — но рабочего способа включить его лектор не нашёл
