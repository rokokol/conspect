# Полнотекстовый поиск
> [!danger] Почему не `LIKE '%слово%'` [49:14](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=2954s)
> Связать поля цепочкой `LIKE` можно, и [[Реляционная модель данных|СУБД]] даже что-то найдёт, но:
> - **медленно** — `LIKE` с ведущим `%` не использует [[Индекс B-tree|индекс]], идёт полный просмотр, не масштабируется с ростом данных;
> - **не учитывает словоформы** — по запросу "мыть раму" документ "мама мыла раму" не найдётся, ведь "мыть" ≠ "мыла" как подстроки;
> - **нет ранжирования** по частоте и близости слов, нет поддержки нескольких языков

## Как устроен полнотекстовый поиск [53:39](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=3219s)
Документ разбирается на фрагменты (слова, пробелы, запятые — по отдельности), фрагменты приводятся к **лексемам** (каноническая форма слова), и на диск кладётся отсортированный набор лексем с **позициями** — где слово встретилось в тексте:

### Зачем нормализовать словоформы [54:35](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=3275s)
Запрос "мягкая булка" должен находить "мягких французских булок". Привести слово к канону можно двумя путями:

> [!abstract] Стемминг против словарей
> - **отрывание окончания** (стемминг, Snowball) — алгоритм, не знающий смысла слов: смотрит на правило и режет. Дёшево, но ошибается — слово "кровать" по суффиксу `-овать` он принимает за глагол и "спрягает";
> - **словари** (Ispell) — знают, что "кровать" существительное, а "ковать" глагол, хотя суффикс похож. Слово не из словаря падает обратно на отрывание окончания

> [!note] Что словарь умеет [59:30](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=3570s)
> - **стоп-слова** — предлоги, артикли (`a`, `the`), которые не индексируются никогда;
> - **синонимы** — поиск может учитывать словарь синонимов;
> - **приведение к канону** — точнее встроенных в СУБД базовых правил;
> - **правила окончаний** — тоже могут жить в словаре

## Словари для русского языка [1:01:14](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=3674s)
Общедоступные словари (Hunspell/MySpell, тот же набор, что в LibreOffice) перекодируют в **UTF-8** (Unicode Transformation Format, 8 бит) и подкладывают к PostgreSQL, затем явно объявляют:

```sql
-- файлы словаря (.dict — части речи, .affix — суффиксы) → tsearch_data/
CREATE TEXT SEARCH DICTIONARY russian_ispell (
    TEMPLATE  = ispell,
    DictFile  = russian,
    AffFile   = russian,
    StopWords = russian
);
CREATE TEXT SEARCH CONFIGURATION russian_ext ( COPY = russian );
ALTER TEXT SEARCH CONFIGURATION russian_ext
    ALTER MAPPING FOR word, hword WITH russian_ispell, russian;
```

## tsvector и tsquery [1:03:31](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=3811s)
> [!important] Два типа данных PostgreSQL
> - **`tsvector`** — подготовленный к поиску текст: отсортированные лексемы с позициями;
> - **`tsquery`** — поисковый запрос. Это полноценные типы, как `text` или `int`

```sql
-- встроенный словарь умеет только рвать окончания → "мам мыл рам"
SELECT to_tsvector('мама мыла раму');
-- 'мам':1 'мыл':2 'рам':3

-- словарь ru: "мама" остаётся "мамой", "раму" → "рама"
SELECT to_tsvector('russian', 'мама мыла раму');
```

[[Регистронезависимый поиск|Регистр не учитывается]] — лексемы приводятся к нижнему. Без явного словаря берётся `default_text_search_config`

> [!tip] Оператор `@@` — соответствует ли текст запросу [1:07:21](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=4041s)
> ```sql
> SELECT to_tsvector('Съешь ещё этих мягких французских булок')
>        @@ plainto_tsquery('мягкая булка');
> -- t  (истина — текст удовлетворяет запросу)
> ```
> - `ts_rank(tsvector, tsquery)` — степень соответствия (абстрактное число вроде `0.98`) для `ORDER BY` в выдаче [1:08:25](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=4105s);
> - `ts_headline(...)` — подсветить найденные слова тегом `<b>` в результате

## Веса частей текста [1:09:20](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=4160s)
> [!note] Слово в заголовке важнее слова в подвале
> Разным частям документа присваивают **метку веса** `A`–`D` функцией `setweight`. Метки нужно проставить **заранее** при индексации — сам по себе текст для СУБД просто набор слов, где заголовок, она не знает:
> ```sql
> SELECT setweight(to_tsvector('заголовок'), 'A') ||
>        setweight(to_tsvector('тело документа'), 'B');
> -- 'заголовок':1A 'тело':2B 'документ':3B   (|| — конкатенация tsvector)
> ```
> В запросе можно потребовать слово только из нужной группы: `to_tsquery('модем:A')` ищет "модем" лишь среди помеченного как `A`

## Всё вместе и индекс [1:11:36](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=4296s)
Под полнотекстовый поиск в таблицу заводят **отдельный столбец** типа `tsvector` и строят по нему индекс:

```sql
CREATE TABLE documents (
    id    SERIAL PRIMARY KEY,
    title TEXT,
    body  TEXT,
    fts   TSVECTOR
);
CREATE INDEX idx_documents_fts ON documents USING GIN (fts);

SELECT * FROM documents WHERE fts @@ to_tsquery('модем');     -- в любой части
SELECT * FROM documents WHERE fts @@ to_tsquery('модем:A');   -- только в заголовке
```

Индекс — типа [[Специализированные индексы (GiST, GIN, битовый)|GIN]]: инвертированный индекс по элементам `tsvector` это его прямое назначение

> [!warning]- Почему нельзя функциональный индекс по `to_tsvector(...)` [1:17:33](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=4653s)
> Соблазн — не держать столбец `fts`, а построить [[Частичный, функциональный и кластерный индексы|функциональный индекс]] прямо по `to_tsvector(body)`. **Нельзя**: функция не [[Хранимые процедуры и функции|`IMMUTABLE`]] — на одних и тех же данных она может дать **разный** результат, ведь словарь и `default_text_search_config` могут поменяться. Функциональный индекс требует стабильной функции, поэтому держат отдельное индексируемое поле
