# Репликация в MySQL
В MySQL **физической репликации нет**: хранение данных отдано подключаемым движкам, у ядра нет единого журнала транзакций, поэтому репликация только [[Физическая и логическая репликация|логическая]] и живёт в **отдельном** журнале

## Сменные движки хранения [28:48](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=1728s)
Хранение отдано подключаемым движкам ([[Архитектура MySQL и движки хранения|InnoDB, MyISAM, Memory и прочие]]), причём в одной базе их можно смешивать — у каждого свои индексы и своё хранение на диске, фактически несколько [[Реляционная модель данных|СУБД]] под одной вывеской. Тот же [[Архитектура MySQL и движки хранения#Цена подключаемости дублирование метаданных|конфликт "простой API против быстрого оптимизатора"]] проходит и через репликацию: ядро плохо видит, что творится внутри движка

## Отдельный журнал репликации [32:25](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=1945s)
> [!note] Журнал транзакций → внутри движка, binlog → отдельно
> У PostgreSQL репликация растёт из общего [[Журнал транзакций (WAL)|журнала транзакций]]. В MySQL такого журнала на уровне ядра нет — он спрятан внутри каждого движка, и для репликации заведён **отдельный бинарный лог** (binlog). "Котлеты отдельно, мухи отдельно". Передавать изменения страниц на диске движки тоже не умеют — значит, в binlog пишутся именно изменения записей

## Режимы репликации [33:38](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=2018s)
> [!example] STATEMENT — повторяем запросы [33:54](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=2034s)
> Самый ранний режим: в лог пишется **сам запрос** в расчёте, что одинаковый `UPDATE` даст одинаковый результат на обеих копиях. Предположение **неверно**:
> ```sql
> UPDATE orders SET created_at = NOW();
> ```
> `NOW()`, автоинкрементные счётчики, случайные значения дадут на репликах **разное** состояние. Пришлось протаскивать в лог подпорки — текущее время, последний выданный `id` и прочее

> [!example] ROW — повторяем изменения записей [34:42](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=2082s)
> В лог пишутся **сами изменённые строки** — гораздо надёжнее, но и данных больше: `DELETE` по условию передаст список всех удалённых записей, а не одну строчку запроса

> [!example] MIXED — по возможности STATEMENT, иначе ROW [35:23](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=2123s)
> Передаём текст запроса, когда он безопасен, и переключаемся на построчную запись, когда запрос потенциально опасен. Запросы [[Определение данных (DDL)|DDL]] всегда передаются как текст

> [!bug]- Хрупкость: MEMORY-таблицы после перезапуска [35:48](https://www.youtube.com/watch?v=HYg6O_YaFEk&t=2148s)
> Передаются изменения таблицы в памяти → реплика перезапускается → прилетает следующее изменение той же таблицы → реплика встаёт, потому что менять нечего: данных в памяти после рестарта нет. Часть запросов в STATEMENT-режиме **гарантированно** рассогласует базы
