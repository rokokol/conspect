# Секционирование таблиц
**Секционирование** (партиционирование) — хранить большую таблицу не единым массивом, а дроблёной на части (по месяцам, неделям). С каждой частью можно работать отдельно: целая секция удаляется мгновенно, а запросы под условие читают только нужную

![[Секционирование таблиц.png]]

## Зачем дробить [1:02:50](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=3770s)
Удалить старую историю обычным `DELETE WHERE day < :month_ago` по таблице в 750 ГБ — значит пройтись по всему объёму и на каждой записи поставить отметку об удалении. Если же данные нарезаны по неделям, лишний отрезок просто **отцепляют целиком**, не пробегая по строкам

> [!summary] Что даёт секционирование [1:05:23](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=3923s)
> - **выборка** под условие читает только подходящие секции;
> - **удаление** старого периода — отцепить/удалить секцию целиком, мгновенно;
> - секции могут лежать на разных дисках, иметь свои индексы и ограничения, обрабатываться независимо при единой структуре

## Реализация через наследование (до PostgreSQL 10) [1:07:56](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=4076s)
Из коробки секционирования в старом PostgreSQL нет — его симулируют через объектную особенность, **наследование таблиц** (тогда как [[Секционирование в MySQL|MySQL делит таблицу декларацией `PARTITION BY` — RANGE/LIST/HASH/KEY]] — ценой жёстких ограничений). Родительская таблица содержит только структуру, в неё никто не пишет; дочерние наследуют её и хранят записи под свой критерий
```sql
CREATE TABLE events (id int, created date);             -- родитель: структура
CREATE TABLE events_2026_06 (
    CHECK (created >= '2026-06-01' AND created < '2026-07-01')
) INHERITS (events);                                    -- секция за июнь
```
Выборка из `events` видит записи всех дочерних таблиц; вставлять же надо явно в нужную секцию

> [!important] Зачем нужен CHECK [1:10:38](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=4238s)
> Ограничение служит двум целям:
> - **защита** от попадания данных не в ту секцию;
> - **отсечение секций** (partition pruning) — по метаданным планировщик знает, что записи `id = 300` в этой секции быть не может, и [[EXPLAIN — план выполнения запроса|в план]] её даже не включает

> [!warning] Индекс не наследуется [1:12:56](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=4376s)
> При `INHERITS` индекс родителя на дочернюю таблицу не переходит — его создают вручную. `CREATE TABLE … (LIKE parent)` тоже копирует поля, но не индекс

## Ограничения костыля [1:16:12](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=4572s)
> [!danger] Это симуляция, а не секционирование из коробки
> - **вставка** только в конкретную дочернюю таблицу — запись в родителя осядет в родителе и сломает всю идею (обходится триггером на родителе, возвращающим `NULL`);
> - [[Целостность и ограничения|внешние ключи]] не работают — либо `FOREIGN KEY`, либо секционирование;
> - на практике у наследования таблиц нет иных применений, кроме секционирования (множественного наследования нет — боулинг, который ещё и кафе, в схему не уложить)

## Готовые решения [1:19:47](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=4787s)
> [!tip] pg_pathman и декларативное секционирование
> - **pg_pathman** — расширение (сделано в России): автоматическое создание секций при вставке, дополнительные оптимизации планировщика. Не входит в комплект, ставится отдельно; внешние ключи по-прежнему не работают
> - **PostgreSQL 10** обещает секционирование из коробки: планировщик знает, что это настоящие секции, и не даёт вставить запись без подходящей секции (`PARTITION BY RANGE`)
