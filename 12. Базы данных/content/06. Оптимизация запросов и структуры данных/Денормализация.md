# Денормализация
**Денормализация** — сознательное нарушение [[Нормальные формы|нормализации]]: мы возвращаем в данные избыточность, чтобы готовый результат лежал рядом и его не приходилось считать заново на каждый запрос

> [!info] Чем платит нормализация
> Нормализация убирает избыточность: данные становятся компактнее (лучше влезают в память → запросы быстрее), их проще менять (правка в одном месте), меньше шансов на противоречие. Но за читаемые "на лету" агрегаты приходится платить — их пересчитывают при каждом обращении

## Зачем нарушать нормализацию [17:44](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=1064s)
В базе кинофильмов оценку каждого фильма ставят пользователи — строк с оценками много. Сервис "лучшие фильмы по жанру" на каждый запрос считает средний рейтинг по всем оценкам: для 60 фильмов про зомби — 82 мс[^recap], но для куда более многочисленных комедий движок перебирает оценки по всей базе и упирается в ~2 ГБ оперативной памяти на запрос и 10 секунд

> [!tip] Рейтинг почти не меняется — а мы считаем его заново
> У большинства фильмов оценка стабильна (старьё никто не пересматривает), у свежих премьер меняется бурно. Но пересчитывать средний рейтинг **на каждый запрос списка** смысла нет — это и есть лишняя работа, которую снимает денормализация

[^recap]: 82 мс — итог оптимизаций из лекции 5 на том же запросе: переписать `JOIN` на [[Подзапросы и обобщённые табличные выражения|подзапрос]] (убрать декартово раздувание тегов × рейтингов), добавить индексы по внешним ключам и [[Покрывающий индекс|покрывающий индекс]] для рейтингов. Суммарно запрос ускорился в 94 раза, но смена жанра снова возвращала 10 секунд

## Рейтинг в самом фильме [18:55](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=1135s)
Кладём рейтинг прямо в запись фильма. Тогда список лучших читается из одной таблицы `films`: зомби — 12 мс, комедии — ~100 мс. Вопрос — как поддерживать значение в актуальном состоянии, пока пользователи продолжают голосовать

![[Денормализация.png]]

> [!warning] Не храним готовое среднее, храним сумму и количество [21:59](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=1319s)
> Среднее = сумма ÷ количество. Если хранить только усреднённое число, новую оценку в него не "доложить". Поэтому в фильм кладут **два** поля — `rating_sum` и `rating_count`; этого достаточно, чтобы и показать средний балл, и обновить его одной оценкой
> ```sql
> ALTER TABLE films ADD COLUMN rating_sum   bigint NOT NULL DEFAULT 0;
> ALTER TABLE films ADD COLUMN rating_count int    NOT NULL DEFAULT 0;
> -- при новой оценке:
> UPDATE films SET rating_sum = rating_sum + :score,
>                  rating_count = rating_count + 1
> WHERE id = :film_id;
> ```

### Как пересчитывать [19:58](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=1198s)
| Способ | Плюс | Минус |
|---|---|---|
| [[Триггеры\|триггер]] на вставку оценки | всегда актуально | лишняя нагрузка на запись; два голоса за один фильм конкурируют за **одну строку**; триггер невидим снаружи |
| пересчёт раз в час | дёшево, просто | значение слегка устаревшее (за час рейтинг резко не меняется) |
| `rating_sum` + `rating_count` + триггер | актуально, среднее считается на лету | поля надо не забыть при любом пути записи оценок |

## Когда денормализация оправдана [23:31](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=1411s)
> [!important] Считать размер избыточности
> Два поля рейтинга занимают мало на фоне записи фильма — выигрыш чистый. А вот затолкать в фильм список **всех тегов** — данные распухнут в разы: читать придётся больше, и выигрыш от убранных соединений уйдёт в ноль или в минус. Денормализуем только то, что не раздувает строку

> [!danger] Денормализацию обязательно документировать [24:39](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=1479s)
> Избыточное поле живёт правильно, только пока **все** пути записи его обновляют. Кто-то сделает новый интерфейс добавления фильмов, забудет про `rating_sum`/`rating_count` — и они навечно устареют, причём молча. Про денормализацию надо помнить и держать её в документации
