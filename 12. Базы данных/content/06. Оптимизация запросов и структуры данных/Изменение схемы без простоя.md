# Изменение схемы без простоя
[[Определение данных (DDL)|Миграции]] и создание индексов берут блокировки, останавливающие сервис. Ограничивают время ожидания блокировки, строят индекс без блокировки записи и меняют тип столбца одним выражением вместо ручной пляски со столбцами[^mysql]

[^mysql]: Все приёмы ниже — про PostgreSQL, где `ALTER` живёт внутри транзакции и откатывается. В [[Изменение схемы в MySQL|MySQL всё жёстче]]: [[Определение данных (DDL)|DDL]] не транзакционен и молча коммитит начатую транзакцию, а `ALTER` на старых версиях пересобирает таблицу целиком

## Ограничить время блокировки [2:00:00](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=7200s)
> [!example] Сорокаминутная заморозка тестового сервера
> Импорт игроков пачкой держал уникальный индекс на имени корабля. Игрок переименовал корабль — и сервер на 40 минут заклинило: ни подтвердить импорт (вдруг откатится), ни разрешить переименование (индекс занят)

> [!success] lock_timeout — либо сейчас, либо никогда [2:01:09](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=7269s)
> Ставят лимит ожидания блокировки: ждать не дольше, скажем, 100 мс, иначе транзакция откатывается. Пользователь получит ошибку и попробует ещё раз, но весь сервис не встанет из-за одной блокировки. Лимит снимает именно ожидание блокировки, а не время полезной работы
> ```sql
> SET lock_timeout = '100ms';
> ```

## Индекс без остановки записи [2:04:42](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=7482s)
> [!note] CREATE INDEX CONCURRENTLY
> Обычный `CREATE INDEX` блокирует таблицу на запись. `CONCURRENTLY` строит [[Индекс B-tree|индекс]] дольше (нужно больше телодвижений ради изоляции), зато без блокировки записи — сервис останавливать не нужно
> ```sql
> CREATE INDEX CONCURRENTLY idx_films_title ON films (title);
> ```

## Смена типа столбца [2:05:38](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=7538s)
> [!example] Из секунд эпохи в timestamp — ручной путь [2:06:02](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=7562s)
> Классическая пляска из четырёх шагов: добавить новый столбец (мгновенно — меняются лишь метаданные, значение везде `NULL`), заполнить его `UPDATE` (долго), удалить старый (мгновенно), переименовать новый в старое имя (мгновенно)

> [!success] ALTER COLUMN … TYPE … USING — одним выражением [2:08:43](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=7723s)
> Тот же результат короче и заметно быстрее: меняем тип столбца, указав, **как** вычислить новое значение из старого
> ```sql
> ALTER TABLE events
>   ALTER COLUMN ts TYPE timestamptz
>   USING to_timestamp(ts);
> ```
