# Постраничная выборка
`LIMIT … OFFSET …` для глубоких страниц дорог: чтобы отдать 100 записей с 21-й страницы, он прочитает 2100 и первые 2000 выбросит. Дешевле прыгнуть к нужному месту по индексу (keyset) или сначала вытащить только идентификаторы

![[Постраничная выборка.png]]

## Проблема LIMIT/OFFSET [33:23](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=2003s)
```sql
SELECT * FROM films ORDER BY title LIMIT 100 OFFSET 2000;
```
Движок прочитает 2100 строк и 2000 благополучно выкинет. Чем дальше страница, тем больше холостой работы

> [!info] Вторую страницу часто никто не открывает[^secondpage]

[^secondpage]: Лектор полгода не замечал, что вторая страница его корпоративного поиска падала с ошибкой — жалоб не было ни одной. Вывод: до второй страницы (после первых ~50 записей) пользователи попросту не доходят

## Пагинация по ключу (keyset) [34:00](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=2040s)
> [!success] Условие "после последней записи" вместо OFFSET
> Запоминаем сортировочный ключ последней показанной строки и просим записи **после** него. По [[Индекс B-tree|индексу]] на поле сортировки движок прыгает прямо к нужному месту и читает ровно 100 строк — без просмотра предыдущих
> ```sql
> SELECT * FROM films WHERE title > :last_title ORDER BY title LIMIT 100;
> ```
> Цена страницы перестаёт зависеть от её номера

## Сначала идентификаторы, потом тяжёлые поля [36:02](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=2162s)
> [!tip] Не таскать обложки сквозь выброшенные строки
> Если в записи лежит тяжёлый атрибут (постер фильма), `OFFSET` вычитывает картинки и у тех 2000 строк, что потом выбросит. Сначала берём только `id` нужной страницы, затем по ним [[Соединения JOIN|соединяем]] полную информацию — картинки читаются лишь для итоговых 100 фильмов
> ```sql
> SELECT f.* FROM films f
> JOIN (SELECT id FROM films ORDER BY title LIMIT 100 OFFSET 2000) p
>   ON p.id = f.id;
> ```
> Чтобы внутренний запрос не вычитывал картинки сам, нужен [[Индекс B-tree|индекс]] по полю сортировки — иначе движок прочитает все строки целиком, чтобы их упорядочить

### Крупные объекты лежат в TOAST отдельно [38:00](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=2280s)
> [!note] Запись не монолитна
> В PostgreSQL гарантированно большие значения (blob, постер) хранятся не вместе со строкой, а в отдельной области — **TOAST** (The Oversized-Attribute Storage Technique, иногда со сжатием). Движок ходит туда только когда поле реально запрошено. Поэтому чтение записи без картинки дёшево, и приём "сначала `id`, потом всё остальное" даёт выигрыш[^logo]

[^logo]: Один и тот же `SELECT DISTINCT` с логотипом компании работал на PostgreSQL на два порядка медленнее, чем на [[Архитектура MySQL и движки хранения|MySQL]]. Причина: для `DISTINCT` PostgreSQL побайтово сравнивал логотипы целиком, а MySQL у объектов больше 1,5 КБ сличает лишь первые ~1 КБ. Убрали логотип из выборки — PostgreSQL снова стал быстрым
