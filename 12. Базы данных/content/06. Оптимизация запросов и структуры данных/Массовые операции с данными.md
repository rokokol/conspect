# Массовые операции с данными
Когда нужно изменить миллионы строк, наивный путь "по записи за раз" либо надолго берёт блокировку, либо гоняет данные по сети поодиночке. Удаление дробят на пачки, обновление сводят к одной временной таблице, вставку отправляют батчем или через `COPY`

## Удаление пачками [1:27:09](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=5229s)
> [!example] Рассылка и чистка внутриигровой почты
> Массовая рассылка письма `INSERT INTO mails …` залочила таблицу на запись — сервер встал на 30 минут, игроков повыкидывало по таймауту. Через месяц удаление протухших писем повторило ту же 30-минутную блокировку

> [!success] Дробить на транзакции [1:29:00](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=5340s)
> Вместо удаления всех писем разом — пачками по 100 000 в отдельных транзакциях. Блокировка держится не на всё удаление, а на одну пачку; суммарно чуть дольше (накладные расходы на транзакции), зато операция размазана по времени и не останавливает остальных
> ```sql
> DELETE FROM mails WHERE id IN (
>     SELECT id FROM mails WHERE created < :older_than LIMIT 100000
> );
> -- повторять, пока есть что удалять
> ```

## Обновление через временную таблицу [1:39:47](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=5987s)
> [!example] 30 000 однотипных UPDATE
> Сменить характеристики 30 000 игровых предметов 30 000 отдельными запросами медленно — каждый выполняется независимо, движок перебирает таблицу снова и снова

> [!success] Загнать в temp-таблицу и обновить одним JOIN
> Создаём временную таблицу соответствия `id → новое значение`, заливаем в неё все 30 000 строк и обновляем единым запросом. Ускорение в тысячи раз — типовой приём для пачки однотипных правок
> ```sql
> CREATE TEMP TABLE item_patch (id int, modifier int);
> -- COPY/INSERT 30000 строк в item_patch
> UPDATE items SET modifier = p.modifier
> FROM item_patch p WHERE items.id = p.id;
> ```

## Массовая вставка [1:45:54](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=6354s)
> [!warning] addBatch обманчив — проверяй, что он делает [1:46:57](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=6417s)
> Почти в любом языке есть пакетная вставка, но проверять надо по факту. [[Модификация данных (DML)|JDBC]]-`addBatch`, если запросить сгенерированные идентификаторы (`INSERT … RETURNING id`), всё равно слал записи **по одной**, ожидая ответ на каждую. Стоит отказаться от возврата ключей — и `executeBatch` отправляет все 100 записей разом, не дожидаясь ответов

> [!tip] COPY для действительно больших объёмов [1:53:07](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=6787s)
> Для миллионов строк — нестандартная команда `COPY`: принимает поток данных (текстовый или двоичный), вставляет только в одну таблицу без условий, блокирует её на запись, но делает вставку очень быстрой. На `COPY` опирается резервное копирование и восстановление: дамп разворачивает схему, заливает данные `COPY FROM`, затем создаёт индексы и ограничения
> ```sql
> COPY films (id, title, year) FROM '/tmp/films.csv' WITH (FORMAT csv);
> ```
