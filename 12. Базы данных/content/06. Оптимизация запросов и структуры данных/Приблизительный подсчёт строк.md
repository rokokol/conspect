# Приблизительный подсчёт строк
`SELECT COUNT(*)` стоит не ноль: из-за [[MVCC]] точное число надо вычислять по индексу. Если устраивает порядок цифры, а не точное значение, количество строк берут из статистики — мгновенно

## Почему COUNT(*) не бесплатен [28:11](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=1691s)
> [!note] Счётчик строк не сохранить заранее
> У каждой транзакции свой срез данных — одна и та же таблица для разных транзакций содержит разное число видимых строк. Поэтому держать единый счётчик нельзя: `COUNT(*)` обязан пройтись по индексу и проверить, какие записи видны **этой** транзакции. Отсюда ненулевая стоимость

## Оценка по статистике [29:55](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=1795s)
[[Реляционная модель данных|СУБД]] держит статистику по таблицам, чтобы строить планы запросов — в ней есть и число записей. Если нам важен только порядок (70 487 516 против 70 488 714 — разницы нет), берём количество прямо из статистики
```sql
SELECT reltuples::bigint AS approx_rows
FROM pg_class WHERE relname = 'films';
```

> [!tip] Точность в обмен на скорость
> Стоимость операции фиксированная и не зависит от размера таблицы. Платим тем, что статистика может быть просрочена — тогда значение будет неактуальным. Но получить примерное число сразу часто полезнее, чем ждать, пока движок прошуршит диском ради точного

## Оценка плана для условного запроса [31:36](https://www.youtube.com/watch?v=9yWZ-LIsAII&t=1896s)
Для "всего результатов: 100" под конкретный фильтр честный `COUNT` может быть долгим. Вместо него спрашивают у планировщика, сколько строк он **ожидает** вернуть — это есть в выводе [[EXPLAIN — план выполнения запроса|EXPLAIN]] (`rows=…`). Число приблизительное, но его можно разобрать программно, завернув в [[Хранимые процедуры и функции|хранимую процедуру]]
