# Уровни изоляции транзакций
[[Определение данных (DDL)|SQL]]-стандарт задаёт **четыре уровня изоляции** — компромисс между параллелизмом и корректностью. Чем выше уровень, тем меньше аномалий он допускает, но тем больше блокировок и тем выше риск отката

> [!important] Уровни и допускаемые аномалии [44:32](https://www.youtube.com/watch?v=XkS3937Xn8M&t=2672s)
>
> | Уровень | Грязное чтение | Неповторяющееся | Фантомное | Аномалия сериализации |
> |---|---|---|---|---|
> | **Read Uncommitted** | ✅ | ✅ | ✅ | ✅ |
> | **Read Committed** | — | ✅ | ✅ | ✅ |
> | **Repeatable Read** | — | — | ✅ | ✅ |
> | **Serializable** | — | — | — | — |
>
> ✅ — аномалия **возможна**, "—" — запрещена. **Потерянное обновление** не допускается **нигде**, даже на самом слабом уровне

> [!warning] Это стандарт и PostgreSQL — MySQL трактует уровни иначе
> Имена уровней у MySQL те же, но [[Уровни изоляции в MySQL|InnoDB на `REPEATABLE READ` допускает фантомы и потерянное обновление]], которые эта таблица запрещает — под MySQL на неё полагаться нельзя

## Аномалии параллельных транзакций [47:02](https://www.youtube.com/watch?v=XkS3937Xn8M&t=2822s)

### Потерянное обновление [47:16](https://www.youtube.com/watch?v=XkS3937Xn8M&t=2836s)
Две транзакции читают одно значение, считают от него и пишут — второй `COMMIT` затирает первый, и одно из изменений пропадает

![[Потерянное обновление.png]]

```sql
-- T1:                                  -- T2:
UPDATE tbl SET f2 = f2 + 20 WHERE f1=1; UPDATE tbl SET f2 = f2 + 25 WHERE f1=1;
```
Запрещено на всех уровнях: [[Реляционная модель данных|СУБД]] заставит вторую транзакцию дождаться первой или откатиться

### Грязное чтение [48:43](https://www.youtube.com/watch?v=XkS3937Xn8M&t=2923s)
Транзакция читает значение, которое другая **ещё не зафиксировала** — а та потом делает `ROLLBACK`. Прочитанных данных "никогда не было"

```sql
-- T1: UPDATE tbl SET f2 = 200 WHERE f1=1;   (ещё не COMMIT)
-- T2: SELECT f2 FROM tbl WHERE f1=1;         -- видит 200
-- T1: ROLLBACK;                              -- а значение откатилось
```

### Неповторяющееся чтение
Транзакция дважды читает **ту же строку** и получает **разные** значения — между чтениями другая транзакция её изменила и закоммитила

```sql
-- T1: SELECT f2 FROM tbl WHERE f1=1;   -- 100
-- T2: UPDATE tbl SET f2 = f2+1 WHERE f1=1; COMMIT;
-- T1: SELECT f2 FROM tbl WHERE f1=1;   -- 101  ← то же чтение, другой результат
```

### Фантомное чтение
Транзакция дважды выполняет **один запрос с условием** и получает **разный набор строк** — другая транзакция вставила/удалила строки, попадающие под условие

```sql
-- T1: SELECT SUM(f2) FROM tbl;          -- X
-- T2: INSERT INTO tbl (f1,f2) VALUES (15,20); COMMIT;
-- T1: SELECT SUM(f2) FROM tbl;          -- X+20  ← появилась "фантомная" строка
```

### Аномалия сериализации [58:15](https://www.youtube.com/watch?v=XkS3937Xn8M&t=3495s)
Самая тонкая: каждая транзакция по отдельности корректна, но их параллельное исполнение даёт результат, **невозможный ни при каком** последовательном порядке. Исключает её только уровень `Serializable`

## Как уровень добивается изоляции: блокировки и откат [39:35](https://www.youtube.com/watch?v=XkS3937Xn8M&t=2375s)
Высокий уровень изоляции реализуется двумя стратегиями — **пессимистичной** (ждать на блокировке) и **оптимистичной** (работать и откатиться при конфликте на коммите):

> [!example] Конфликт на Repeatable Read
> Две транзакции на `REPEATABLE READ` прочитали один баланс и обе пытаются его увеличить. Первая коммитится успешно, а вторая получает
> ```
> ERROR: could not serialize access due to concurrent update
> ```
> и должна **повторить** всю транзакцию заново. Это оптимистичный подход: вместо ожидания на блокировке СУБД даёт работать, но при обнаруженном конфликте откатывает "проигравшего"

> [!tip] Явная пессимистичная блокировка — SELECT … FOR UPDATE
> Чтобы не ловить откат, строку можно заблокировать на чтении [[Выборка данных (SELECT)|`SELECT … FOR UPDATE`]]: другие транзакции будут **ждать**, пока текущая не завершится. Цена — потерянный параллелизм на этой строке
