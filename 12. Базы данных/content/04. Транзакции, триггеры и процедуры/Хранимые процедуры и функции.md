# Хранимые процедуры и функции
Код на стороне сервера, исполняемый внутри [[Реляционная модель данных|СУБД]]. Разница принципиальная: **функция** возвращает значение и вызывается **внутри запроса**, а **процедура** — самостоятельная команда, которая умеет **управлять транзакциями** (`COMMIT`/`ROLLBACK` внутри себя, с PostgreSQL 11)

| | Функция | Процедура |
|---|---|---|
| Вызов | внутри `SELECT`/`WHERE` как выражение | отдельной командой `CALL` |
| Возвращает | значение или набор строк | ничего (или через параметры) |
| Транзакции внутри | **нельзя** (работает в чужой транзакции) | **можно** `COMMIT`/`ROLLBACK` |

## Функции на разных языках [1:09:02](https://www.youtube.com/watch?v=XkS3937Xn8M&t=4142s)
Тело функции пишут на разных языках через `LANGUAGE`: чистый `SQL`, процедурный `plpgsql`, а также `plpythonu`, `plperl` и другие

```sql
-- простая SQL-функция
CREATE FUNCTION add(integer, integer) RETURNS integer
  AS 'SELECT $1 + $2;'
  LANGUAGE SQL IMMUTABLE RETURNS NULL ON NULL INPUT;

-- процедурная на PL/pgSQL
CREATE OR REPLACE FUNCTION inc(i integer) RETURNS integer AS $$
BEGIN
  RETURN i + 1;
END;
$$ LANGUAGE plpgsql;
```

> [!tip] Категория изменчивости — подсказка оптимизатору [1:11:34](https://www.youtube.com/watch?v=XkS3937Xn8M&t=4294s)
> Функцию помечают по тому, от чего зависит её результат — это позволяет [[Оптимизатор запросов|оптимизатору]] кешировать вызовы:
> - **`IMMUTABLE`** — результат зависит только от аргументов (`add(2,3)` всегда `5`) → можно вычислить один раз;
> - **`STABLE`** — не меняется в пределах одного запроса, но зависит от состояния [[Реляционная модель данных|БД]];
> - **`VOLATILE`** (по умолчанию) — может меняться при каждом вызове (`now()`, `random()`) → пересчитывается каждый раз

## PL/pgSQL: управляющие конструкции
Процедурный язык даёт ветвления, циклы и обход результата запроса:

```sql
IF cond THEN ... ELSIF cond THEN ... ELSE ... END IF;

FOR i IN 1..10 LOOP ... END LOOP;            -- 1,2,…,10
FOR i IN REVERSE 10..1 BY 2 LOOP ... END LOOP; -- 10,8,6,4,2

WHILE amount > 0 LOOP ... END LOOP;

FOR row IN SELECT * FROM cs_views ORDER BY sort_key LOOP
  EXECUTE format('TRUNCATE TABLE %I', row.name);  -- динамический SQL
END LOOP;
```

> [!example]- Процедура, управляющая транзакциями
> С PostgreSQL 11 процедура может коммитить/откатывать **внутри** цикла — каждая итерация фиксируется отдельно:
> ```sql
> CREATE PROCEDURE transaction_test1() AS $$
> BEGIN
>   FOR i IN 0..9 LOOP
>     INSERT INTO test1 (a) VALUES (i);
>     IF i % 2 = 0 THEN COMMIT;       -- чётные фиксируем
>     ELSE ROLLBACK;                  -- нечётные откатываем
>     END IF;
>   END LOOP;
> END $$ LANGUAGE plpgsql;
> ```
> Функция так не умеет — она исполняется внутри транзакции вызывающего

## За и против серверного кода [1:13:36](https://www.youtube.com/watch?v=XkS3937Xn8M&t=4416s)

> [!check] Плюсы
> - **инкапсуляция** логики — одна реализация на все приложения;
> - **меньше сетевого трафика** — тяжёлая обработка идёт рядом с данными, не гоняя их на клиент;
> - **разграничение доступа** — пользователю дают вызывать процедуру (`SECURITY DEFINER`), но не трогать таблицы напрямую — слой защиты данных

> [!fail] Минусы
> - **нагрузка на сервер БД** — масштабировать его сложнее, чем приложения;
> - **дублирование логики** — часть кода в приложении, часть в БД;
> - **сложность миграции** — синтаксис процедур у СУБД свой, перенос между движками болезненный
