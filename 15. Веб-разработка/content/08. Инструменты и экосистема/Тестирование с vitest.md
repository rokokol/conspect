# Тестирование с vitest
**Vitest** — тест-раннер из экосистемы Vite: находит файлы `*.test.js`, выполняет и сверяет ожидания[^1]. Главная ценность тестов — не "поймать баг сейчас", а **защита от регрессий**: смелость менять код, зная, что поломку старого поведения поймает машина, а не пользователь. Весь этот курс ты уже живёшь внутри vitest — каждое упражнение проверяется им

[^1]: Генеалогия: Jasmine (2010) придумала синтаксис describe/it/expect → Facebook собрал Jest (2014), стандарт эпохи → Vitest (2021, Anthony Fu и команда Vite) взял [[Программный интерфейс приложения|API]] Jest почти дословно, но на нативных [[Модули|ESM]] и с переиспользованием конфига Vite. Совместимость сознательная: миграция с Jest часто сводится к замене импорта

## Анатомия теста

```js
import { describe, test, expect } from "vitest";
import { nextInterval } from "./srs.js";

describe("nextInterval", () => {                    // группа (необязательна)
  test("удваивает интервал при good", () => {
    expect(nextInterval(4, "good")).toBe(8);        // Arrange–Act–Assert в одну строку
  });

  test("сбрасывает при again", () => {
    expect(nextInterval(16, "again")).toBe(1);
  });
});
```

Схема каждого теста — **AAA** (Arrange–Act–Assert): подготовь данные, вызови, проверь. Один тест — одно утверждение о поведении; имя теста — читаемое предложение, вместе они складываются в спецификацию функции

### Матчеры

| Матчер | Проверяет | Нюанс |
|---|---|---|
| `toBe(x)` | `Object.is` — идентичность | для примитивов |
| `toEqual(x)` | глубокое структурное равенство | для объектов/массивов |
| `toThrow(/msg/)` | функция бросает | передавать `() => f()`, не `f()` |
| `resolves` / `rejects` | промисы | `await expect(p).resolves.toBe(1)` |
| `toContain`, `toMatch` | вхождение / регэксп | массивы и строки |
| `toBeCloseTo(0.3)` | числа с плавающей точкой | `0.1 + 0.2` — [[Типы и коэрция|помним]] |

`test.each` гоняет один тест по таблице случаев — то, чем сделаны квизы этого курса:

```js
test.each([
  [1, "good", 2],
  [8, "easy", 24],
])("interval(%i, %s) → %i", (d, grade, want) => {
  expect(nextInterval(d, grade)).toBe(want);
});
```

## Моки

Юнит-тест должен быть быстрым и детерминированным, а реальность (сеть, время, случайность) — нет. **Мок** (mock) — управляемая подделка зависимости

```js
import { vi } from "vitest";

const fn = vi.fn().mockReturnValue(42);   // функция-шпион: помнит вызовы
fn(1); fn(2);
expect(fn).toHaveBeenCalledTimes(2);
expect(fn).toHaveBeenCalledWith(1);

vi.useFakeTimers();                       // время — под контроль
vi.setSystemTime(new Date("2026-07-18"));
vi.advanceTimersByTime(60_000);           // "прошла минута" мгновенно — debounce тестируется без ожидания
```

> [!warning] Мокай границы, а не внутренности
> Если для теста приходится мокать половину собственного модуля — архитектура сопротивляется. Здоровый паттерн: чистая логика (вычисления, [[Хранение данных в браузере|store]]) тестируется без моков вообще, моки — только на границах с миром: `fetch`, таймеры, [[HTML-документ и DOM-дерево|DOM]]. Это тот же аргумент, что двигал [[Формы из JavaScript|отделение логики от UI]]: тестируемость — побочный продукт хорошего разделения

## Режимы запуска

```bash
npx vitest              # watch: перезапуск при сохранении — основной режим разработки
npx vitest run          # одноразово (CI); npm test у нас — это он
npx vitest run 04       # фильтр по пути — только модуль 04
npx vitest --coverage   # покрытие: какие строки кода тесты вообще выполняли
```

> [!note] Покрытие — термометр, не цель
> 100% coverage не гарантирует корректность (можно выполнить строку, ничего не проверив), а погоня за цифрой порождает бессмысленные тесты. Польза обратная: *низкое* покрытие честно показывает, куда тесты не заглядывали никогда

## Культура

- **Красный сначала**: увидь тест падающим до того, как он позеленеет, — иначе не знаешь, проверяет ли он хоть что-то. Радикальная версия — **TDD** (Test-Driven Development): тест пишется *до* кода, цикл "красный → зелёный → рефакторинг"[^2]
- **Тестируй поведение, не реализацию**: тест "функция возвращает отсортированный список" переживёт смену алгоритма, тест "функция вызывает `.sort()`" — нет
- **Баг = сначала тест**: воспроизвёл падением, починил, тест остался часовым против возврата
- Тесты — исполняемая документация: лучший способ понять чужую библиотеку — открыть её `*.test.*`

[^2]: У vitest есть режим, доводящий "тест рядом с кодом" до предела: **in-source testing** — блок `if (import.meta.vitest) { … }` с тестами прямо в файле реализации, из прод-сборки вырезается бандлером как мёртвый код. Идея подсмотрена у Rust, где `#[test]`-функции традиционно живут в том же файле, что и код
