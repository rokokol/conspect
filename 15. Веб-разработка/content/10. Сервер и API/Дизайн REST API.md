# Дизайн REST API
**REST** (Representational State Transfer — передача представления состояния) — стиль проектирования [[Программный интерфейс приложения|API]] поверх [[HTTP]]: мир описывается **ресурсами** (существительные в [[URL и адресация|URL]]), действия над ними — стандартными методами[^1]. Хороший REST API читается без документации: URL говорит *что*, метод — *что сделать*, статус — *что вышло*

[^1]: Термин — из диссертации Роя Филдинга (2000), соавтора спецификации HTTP/1.1. Академический REST требует ещё и HATEOAS (Hypermedia As The Engine Of Application State — ответы несут ссылки на возможные дальнейшие действия, клиент ничего не знает заранее); индустрия взяла примерно половину идей, и Филдинг годами сердито писал, что "RESTful API" на [[Слабоструктурированные данные и JSON|JSON]] RESTом не являются. Практический словарь победил: сегодня REST = "HTTP + JSON + ресурсные URL по конвенциям"

## Ресурсы и методы

Сквозной пример модуля — API колоды карточек (реализация — [[Сервер на Hono и SQLite|следующая заметка]]):

| Запрос | Смысл | Ответ |
|---|---|---|
| `GET /cards` | список карточек | 200 + конверт со списком |
| `GET /cards/42` | одна карточка | 200 или 404 |
| `POST /cards` | создать (тело — JSON) | **201** + созданное |
| `PATCH /cards/42` | изменить частично | 200 + новое состояние |
| `PUT /cards/42` | заменить целиком | 200 |
| `DELETE /cards/42` | удалить | **204** без тела |
| `POST /cards/42/review` | доменное действие вне CRUD | 200 |

Конвенции: существительные во множественном числе (`/cards`, не `/getCard`), вложенность выражает принадлежность (`/decks/3/cards`), глагол в URL допустим только для действия, не сводящегося к **CRUD** (Create, Read, Update, Delete — четвёрка базовых операций)

## Идемпотентность как контракт с сетью

| Метод | Safe (не меняет состояние) | Идемпотентный (повтор безвреден) |
|---|---|---|
| GET / HEAD | ✅ | ✅ |
| PUT / DELETE | ❌ | ✅ |
| POST | ❌ | ❌ |
| PATCH | ❌ | ❌ в общем случае |

Это не педантизм, а обещания, на которые опирается чужая инфраструктура. Сеть моргнула, ответ потерялся — клиент **ретраит**: идемпотентный запрос можно повторить слепо, POST — нельзя (два платежа). Safe-методы прокси кэшируют, краулеры дёргают, браузер повторяет без спроса — GET, меняющий данные, рано или поздно взорвётся[^2]

[^2]: Хрестоматийный взрыв — Google Web Accelerator (2006): плагин-ускоритель префетчил все ссылки на странице и начал массово удалять данные в веб-приложениях, где "удалить" было обычной ссылкой `<a href="/delete?id=…">`, то есть GET-ом. Нарушителями контракта были приложения, но досталось всем. Для неидемпотентных POST придуман обходной паттерн **Idempotency-Key** (Stripe и платёжные API): клиент шлёт с запросом случайный ключ, сервер запоминает результат и на повтор с тем же ключом отвечает сохранённым ответом, не выполняя операцию дважды

## Статусы и ошибки

Рабочая обойма: `200` ок / `201` создано / `204` ок без тела / `400` кривой синтаксис / `401` кто ты? / `403` тебе нельзя / `404` нет такого / `409` конфликт (логин занят) / `422` JSON валиден, данные — нет / `429` слишком часто / `500` мы сломались

Ошибка 4xx обязана объясняться телом — машиночитаемо, а не прозой:

```json
{ "error": { "code": "validation", "message": "front: обязательное поле", "field": "front" } }
```

Для этого есть и стандарт **[[RFC]] 9457** `application/problem+json` (поля `type`, `title`, `detail`, `status`); главное свойство любого формата — консистентность: один формат ошибок на весь API, чтобы клиент писал один обработчик

## Коллекции

Вариации чтения — параметрами запроса: `GET /cards?status=due&sort=createdAt&limit=50&offset=100`. Отдавать таблицу целиком нельзя — **пагинация** обязательна с первого дня, и у неё две школы:

| | offset/limit | курсорная |
|---|---|---|
| запрос | `?offset=100&limit=50` | `?cursor=eyJpZCI6NDJ9&limit=50` |
| реализация | тривиальна (`LIMIT ? OFFSET ?`) | сервер отдаёт непрозрачный курсор "после этого элемента" ([[Постраничная выборка#Пагинация по ключу (keyset) [34 00](https //www.youtube.com/watch?v=9yWZ-LIsAII&t=2040s)\|keyset]]) |
| вставили/удалили строку во время обхода | страницы съезжают: дубли и пропуски | обход стабилен |
| прыжок на страницу N | ✅ | ❌ только вперёд |

Ответ — конверт с метаданными: `{ "items": […], "total": 1200, "nextCursor": "…" }`. Голый массив в корне ответа — тупик: добавить `total` потом будет несовместимой сменой формата

> [!warning] API — это обещание
> Опубликованный эндпоинт нельзя менять несовместимо: чужой код уже на него рассчитывает — тот же [[Node и npm#Semver|дух semver]]. Добавлять поля можно (клиент обязан игнорировать незнакомое), переименовывать и удалять — только с версией: путь `/api/v2/…` или заголовок. Дешевле проектировать так, чтобы v2 не понадобился: минимум полей, скучные имена, конверты вместо голых массивов

> [!tip] Думай curl-ом
> Тест дизайна: любая операция API показывается однострочником `curl -X POST …/cards -H 'content-type: application/json' -d '{"front":"…"}'`. Если для объяснения эндпоинта нужен абзац про особые заголовки и порядок вызовов — дизайн пахнет. Следующий уровень той же идеи — **OpenAPI**: машиночитаемое описание всех эндпоинтов, из которого генерируются документация, клиенты и валидаторы
