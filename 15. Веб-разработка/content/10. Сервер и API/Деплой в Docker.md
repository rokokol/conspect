# Деплой в Docker
**Docker** упаковывает приложение со всеми зависимостями в **образ** (image) — неизменяемый снимок [[Файловая система|файловой системы]] — и запускает его **контейнером**: изолированным процессом со своей [[Файловая система|ФС]], сетью и лимитами[^1]. Решаемая проблема стара как деплой: "у меня работает" перестаёт быть аргументом, потому что везде запускается одно и то же

[^1]: Контейнер — не виртуальная машина: ядро [[Операционная система|ОС]] общее, изоляцию дают механизмы Linux (namespaces прячут чужие процессы и сеть, cgroups режут ресурсы), поэтому старт — миллисекунды. Технологии к тому моменту было лет двадцать (chroot, FreeBSD jails, LXC — Linux Containers); Docker (2013, pivot умирающего хостинга dotCloud) добавил "всего лишь" удобство — Dockerfile + реестр готовых образов — и этого хватило перевернуть индустрию. Идейный родственник твоего NixOS: воспроизводимость описанием, а не ритуалом

## Dockerfile

```dockerfile
FROM node:22-slim              # базовый слой: Debian + Node
WORKDIR /app
COPY package*.json ./          # сначала только манифесты…
RUN npm ci --omit=dev          # …слой пересобирается лишь при смене зависимостей
COPY src ./src                 # код меняется часто — он ниже
ENV NODE_ENV=production
USER node                      # не root: взлом процесса ≠ root в контейнере
EXPOSE 3000
CMD ["node", "src/index.js"]
```

```bash
docker build -t deck-api .
docker run -p 3000:3000 deck-api
```

Каждая инструкция — **слой** с кэшем: не изменился вход — слой берётся готовым. Отсюда главный приём Dockerfile: *редко меняющееся выше, часто меняющееся ниже* — зависимости ставятся заново при правке package.json, а не при каждой правке кода. `.dockerignore` (node_modules, .git, *.sqlite) обязателен: без него локальный мусор едет в контекст сборки и ломает кэш

> [!note] Multi-stage — сборка отдельно, рантайм отдельно
> Если для сборки нужны devDependencies ([[Система типов TypeScript|TS]], бандлер), их не тащат в прод-образ: первая стадия `FROM node AS build` собирает, вторая копирует из неё только артефакты — `COPY --from=build /app/dist ./dist`. Образ худеет в разы, и в нём нет ни компиляторов, ни исходников. Наш сервер на чистом [[Типы и коэрция|JS]] обходится одной стадией, но приём понадобится сразу же, как в контейнер поедет TypeScript

## docker compose

Флаги `docker run` не живут в голове; **compose** описывает запуск файлом:

```yaml
# docker-compose.yml
services:
  api:
    build: .
    ports:
      - "3000:3000"            # хост:контейнер
    environment:
      DB_PATH: /data/deck.sqlite
    volumes:
      - ./data:/data           # база переживает контейнер
    restart: unless-stopped
```

```bash
docker compose up -d --build   # поднять; -d — в фоне
docker compose logs -f api     # хвост логов
docker compose down            # погасить
```

> [!warning] Контейнер эфемерен — данные снаружи ^volume-persist
> Файловая система контейнера умирает вместе с ним: пересобрал — база пропала. Всё живое (наш [[Сервер на Hono и SQLite|SQLite-файл]]) выносится в **volume** — папку хоста, примонтированную внутрь. Проверка на себе: `docker compose down && docker compose up -d`, карточки на месте? Это репетиция главного вопроса любого деплоя — "что переживает перезапуск"

## Остановка по SIGTERM

`docker stop` (и любой рестарт compose) шлёт процессу **SIGTERM**, ждёт 10 секунд и добивает SIGKILL. Node по умолчанию на SIGTERM просто умирает — вместе с запросами в полёте. Обработчик из [[Node как рантайм#process|заметки про process]] здесь перестаёт быть теорией: закрыть сервер, дождаться текущих ответов, закрыть базу, выйти нулём

Бонус-грабля: `CMD` в форме строки (`CMD node src/index.js`) запускает процесс через `sh -c`, и сигнал получает sh, а не Node, — потому `CMD` пишут [[Слабоструктурированные данные и JSON|JSON]]-массивом

## Жизнь работающего сервиса

| Команда | Зачем |
|---|---|
| `docker ps` | что запущено, какие порты |
| `docker compose exec api sh` | шелл внутри контейнера: посмотреть глазами |
| `docker stats` | память и [[Центральный процессор\|CPU]] по контейнерам |
| `docker system prune` | прибрать старые образы (копятся гигабайтами) |

Деплой на реальный сервер — тот же compose на арендованной машине: `git pull && docker compose up -d --build`. Твоя 3x-ui-панель на VPN-нодах так и живёт. Статике всё это не нужно — ей хватит [[Деплой сайта|хостинга попроще]]

> [!tip] Логи — в stdout, и точка
> Контейнерное приложение не пишет логи в файлы — просто `console.log`: сбор и хранение — забота платформы (`docker logs`, journald, что угодно). Ещё один пункт twelve-factor, и он же объясняет, почему серверные фреймворки логируют в консоль без затей — файл с ротацией был бы ложной ответственностью приложения
