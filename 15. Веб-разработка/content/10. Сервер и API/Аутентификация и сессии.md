# Аутентификация и сессии
**Аутентификация** — проверка "ты действительно ты" (пароль, ключ); **авторизация** — "тебе это можно" (права). Статусы их различают: 401 — не аутентифицирован (имя Unauthorized исторически неточное), 403 — аутентифицирован, но нельзя

## Пароли

Пароли **не хранятся** — в базе лежит необратимый отпечаток. Проверка = захэшировать введённое и сравнить. Хэш для паролей обязан быть *медленным* — обычные [[SHA-256]] и MD5 дисквалифицированы, потому что перебираются миллиардами в секунду на одной видеокарте:

```js
import { scryptSync, randomBytes, timingSafeEqual } from "node:crypto";

const salt = randomBytes(16).toString("hex");
const hash = scryptSync(password, salt, 64).toString("hex");
// в базу: `${salt}:${hash}`; проверка — scrypt от ввода с ТОЙ ЖЕ солью + timingSafeEqual
```

- **соль** — случайная добавка на каждого пользователя: одинаковые пароли дают разные хэши, предвычисленные словари хэшей (радужные таблицы) бесполезны[^1]
- **scrypt / bcrypt / argon2** — функции, намеренно дорогие по времени *и памяти* (память — защита от [[Графический процессор|GPU]]: видеокарта считает быстро, но памяти на тысячи параллельных попыток у неё нет); argon2 — победитель конкурса Password Hashing Competition (2015), scrypt хорош тем, что уже в `node:crypto`
- **timingSafeEqual** вместо `===` — сравнение за постоянное время: обычное сравнение строк выходит на первом несовпавшем байте, и по времени отказа секрет подбирается посимвольно (тайминг-атака)

[^1]: Хрестоматийная утечка — LinkedIn (2012): 117 млн хэшей SHA-1 без соли; сообщество восстановило ~90% паролей за считаные дни. Слитые bcrypt-базы, для сравнения, почти бесполезны атакующему. Рабочая презумпция с тех пор: база утечёт — храни так, чтобы это не стало катастрофой

## Сессии

[[HTTP#Cookies|HTTP не помнит]] предыдущих запросов; логин должен прилипнуть. Классика — серверная сессия:

```mermaid
sequenceDiagram
    participant B as браузер
    participant S as сервер
    B->>S: POST /login {login, password}
    S->>S: scrypt-проверка, создать сессию sid=af3…
    S-->>B: Set-Cookie: sid=af3…; HttpOnly; Secure; SameSite=Lax
    B->>S: GET /cards (cookie едет сам)
    S->>S: сессия af3… → user 7
    S-->>B: 200, карточки пользователя 7
```

Сервер хранит `sid → { userId, expiresAt }` (таблица в [[Сервер на Hono и SQLite|SQLite]] годится), браузер — только непрозрачный идентификатор. `sid` — это `randomBytes(32)`: криптослучайность обязательна, инкремент или timestamp перебираются. Выход = удалить строку — сессия отзывается мгновенно

> [!important] Три флага cookie сессии — не обсуждаются
> - **HttpOnly** — cookie невидима для [[Типы и коэрция|JS]]: [[Безопасность в браузере#XSS|XSS]] не уносит сессию
> - **Secure** — только по [[HTTP|HTTPS]]
> - **SameSite=Lax** — не едет с межсайтовым POST: [[Безопасность в браузере#CSRF|CSRF]] закрыт почти целиком (остаток — CSRF-токен в форме, если [[Программный интерфейс приложения|API]] зовут из старых браузеров или с `SameSite=None`)
>
> Отсюда же ответ на вечный вопрос "где хранить токен на клиенте": не в localStorage (его читает любой XSS), а в HttpOnly-cookie — браузер сам прикладывает её к запросам, коду она недоступна

> [!warning] Фиксация сессии
> Сценарий атаки: жертве подсовывают заранее известный `sid` (ссылкой, скриптом), она логинится — атакующий входит по тому же `sid` уже аутентифицированным. Лекарство — **перегенерировать идентификатор при логине**: старый `sid` умирает, новый выдаётся только в `Set-Cookie` ответа на успешный вход
>
> Плюс гигиена: срок жизни ограничен, активная сессия продлевается, на `/login` — rate limit (боты перебирают пароли на любом публичном порту — увидишь в логах своего деплоя)

## JWT

**JWT** ([[Слабоструктурированные данные и JSON|JSON]] Web Token) — подписанный сервером токен, несущий данные в себе: `header.payload.signature`. Payload — читаемый base64 (кодирование, не шифрование!), подпись гарантирует целостность; сервер ничего не хранит — только проверяет подпись

| | Серверная сессия | JWT |
|---|---|---|
| хранение на сервере | таблица сессий | нет |
| мгновенный отзыв | ✅ удалил строку | ❌ жив до истечения срока |
| много серверов | нужен общий стор | ✅ проверка локальна |
| размер в каждом запросе | ~32 байта | сотни байт |

Для приложения с одной базой серверные сессии проще и безопаснее; JWT силён между сервисами и на edge, где общего стора нет. Мода "JWT везде" — источник классических дыр: токены в localStorage, невозможность разлогинить украденный токен, историческая атака `alg: none` (библиотеки принимали токен, в заголовке которого атакующий сам объявил "подписи нет")[^2]

[^2]: Смежные термины, чтобы не путались: **OAuth** — протокол *делегирования* доступа ("пусти это приложение к моему GitHub без пароля"), **OpenID Connect** поверх него — вход через чужой аккаунт ("Sign in with Google"). JWT там — формат билетов. Для собственного логина, как у нас, они не нужны; понадобятся, когда захочешь "войти через GitHub" вместо своей таблицы паролей
