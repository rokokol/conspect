# Производительность страницы
Производительность веба — **воспринимаемая**: пользователю не важны миллисекунды сами по себе, важно "быстро появилось, не прыгает, откликается". Индустриальный стандарт этой троицы — **Core Web Vitals** (базовые веб-показатели, метрики Google)[^1]

| Метрика | Расшифровка | Меряет | Хорошо |
|---|---|---|---|
| **LCP** | Largest Contentful Paint | когда отрисован самый крупный элемент — "страница появилась" | ≤ 2.5 с |
| **INP** | Interaction to Next Paint | от действия пользователя до следующего кадра — "откликается" | ≤ 200 мс |
| **CLS** | Cumulative Layout Shift | суммарная прыгучесть вёрстки — "не уезжает из-под пальца" | ≤ 0.1 |

[^1]: Метрики — не только гигиена: с 2021 Core Web Vitals — сигнал ранжирования Google ([[SEO и метаданные|модуль 11]]), медленный сайт ниже в выдаче. Классика жанра — внутренние исследования гигантов: Amazon оценивал +100 мс задержки в −1% продаж, Google — +500 мс поиска в −20% трафика. INP в наборе недавно — в 2024 заменил слишком снисходительный FID (First Input Delay), который мерял лишь задержку *начала* обработки

## Профилирование

Правило номер ноль: **не оптимизируй вслепую** — сначала измерь, где на самом деле горит. DevTools → Performance: запись ленты кадров

- **Flame chart** — "пламя" стеков вызовов: ширина = длительность; красные треугольники — **long tasks** (>50 мс, блокируют отклик)
- **Bottom-Up** — та же запись, сгруппированная по функциям: кто суммарно съел больше всех
- Полосы Layout / Paint в ленте — привет от [[Рендер-пайплайн|пайплайна]]: фиолетовая стена Layout = layout thrashing виден буквально глазами

> [!important] Троттлинг — обязательный ритуал
> Твоя машина с NVMe и гигабитом — худший в мире прибор для оценки скорости сайта. В Performance panel всегда: **[[Центральный процессор|CPU]] 4× slowdown + Network Fast 4G** — примерно средний телефон пользователя. Разница с "у меня всё летает" бывает десятикратной

**Lighthouse** (вкладка DevTools) — автоаудит: прогоняет страницу и выдаёт отчёт с конкретными виновниками ("картинка 4 МБ", "шрифт блокирует рендер"). Точечные замеры своего кода — `performance.mark("a")` / `performance.measure("a→b", "a", "b")`: появляются прямо в ленте Performance

## Загрузка

Браузер не может рисовать, пока не получит критический минимум: [[HTML-документ и DOM-дерево|HTML]] + **блокирующий [[Каскад и селекторы|CSS]]** (+ синхронные скрипты, [[Как браузер превращает ответ в пиксели#Докачка ресурсов|стоп-кран парсера]]). Отсюда рычаги:

| Приём | Эффект |
|---|---|
| `<script defer>` / `type="module"` | [[Типы и коэрция\|JS]] не блокирует парсинг |
| `width`/`height` у `<img>` | место зарезервировано → CLS не прыгает |
| `loading="lazy"` у картинок ниже экрана | не грузим невидимое |
| современные форматы (WebP/[[Медиа и таблицы\|AVIF]]) | −30–70% веса картинок |
| `font-display: swap` у @font-face | текст виден системным шрифтом, пока едет свой |
| code splitting у [[Бандлеры|бандлера]] | грузится только нужное сейчас |
| `<link rel="preload">` / `preconnect` | важное качается раньше, чем браузер сам догадается |

Самая частая победа скучна: **вес**. Мировая медиана страницы — за 2 МБ, из них львиная доля — картинки и чужие скрипты аналитики; аудит трёх тегов `<script>` от маркетинга часто даёт больше, чем неделя оптимизации кода

## Отзывчивость

INP портят длинные таски на main thread. Рецепты: дробить работу (`setTimeout(0)`-порциями или `scheduler.yield()`), выносить тяжёлое в [[Параллельность, гонки и отмена|Web Worker]], для гигантских списков — виртуализация (рендерить только видимые строки, [[HTML-документ и DOM-дерево|DOM]] на 50 000 `<li>` не прощается)

> [!tip] Профиль сначала, оптимизация потом — это цитата
> "Premature optimization is the root of all evil" Кнута обычно обрезают; полностью она честнее: *в ~97% случаев* микрооптимизации — зло, *но упускать критические 3% нельзя*. Профилировщик и существует, чтобы найти эти 3% — а не угадывать их по вкусу
