# HTTP
**HTTP** (HyperText Transfer Protocol) — текстовый протокол "запрос → ответ" поверх [[Заголовок TCP и установление соединения|TCP]]. Всё, что делает веб — загрузка страниц, отправка форм, [[Программный интерфейс приложения|API]], — это его сообщения

## Формат сообщений

Запрос и ответ устроены зеркально: стартовая строка → заголовки → пустая строка → тело

```http
GET /notes/web HTTP/1.1          ← метод, путь, версия
Host: example.org                ← заголовки запроса
User-Agent: curl/8.9
Accept: text/html
                                 ← пустая строка = конец заголовков
```

```http
HTTP/1.1 200 OK                  ← версия, статус-код, пояснение
Content-Type: text/html; charset=utf-8
Content-Length: 1256

<!DOCTYPE html>…                 ← тело ответа
```

## Методы

| Метод | Семантика | Тело запроса | Свойства |
|---|---|---|---|
| `GET` | дай ресурс | нет | safe, идемпотентен |
| `HEAD` | дай только заголовки | нет | safe, идемпотентен |
| `POST` | создай / обработай (формы, API) | есть | ни то ни то |
| `PUT` | замени ресурс целиком | есть | идемпотентен |
| `PATCH` | измени частично | есть | нет |
| `DELETE` | удали | обычно нет | идемпотентен |
| `OPTIONS` | что ты умеешь? (важен для [[CORS на практике\|CORS]]) | нет | safe |

> [!note] Safe и идемпотентность
> **Safe** — метод не меняет состояние сервера (можно кэшировать, предзагружать). **Идемпотентный** — повтор запроса не меняет результат: `DELETE` дважды = `DELETE` один раз, а вот два `POST` создадут две записи. Поэтому браузер переспрашивает "отправить форму повторно?" именно на POST

## Статус-коды

Первая цифра — класс ответа:

| Класс | Смысл | Знаковые коды |
|---|---|---|
| 1xx | информационные | 101 Switching Protocols (WebSocket) |
| 2xx | успех | **200** OK, 201 Created, 204 No Content |
| 3xx | редиректы | **301** навсегда, **302** временно, **304** Not Modified — бери из кэша |
| 4xx | ошибка клиента | 400 Bad Request, 401 не авторизован, 403 запрещено, **404** нет такого, 429 слишком часто |
| 5xx | ошибка сервера | **500** Internal Server Error, 502 Bad Gateway, 503 перегружен |

> [!warning] 401 против 403
> **401 Unauthorized** — "я не знаю, кто ты" (нужен логин); **403 Forbidden** — "я знаю, кто ты, и тебе нельзя". Название 401 исторически неточное — по смыслу это unauthenticated[^1]

[^1]: В стандарте есть и шуточный **418 I'm a teapot** — из первоапрельского [[RFC]] 2324 про протокол управления кофеварками. Код прижился: его реально возвращают серверы, не желающие обслуживать подозрительный запрос

## Заголовки, которые встречаются каждый день

| Заголовок               | Сторона        | Зачем                                                                |
| ----------------------- | -------------- | -------------------------------------------------------------------- |
| `Host`                  | запрос         | какой из сайтов на этом [[IP-адрес и маска подсети\|IP]] нужен — обязателен с HTTP/1.1             |
| `User-Agent`            | запрос         | кто клиент; сервер может отдавать разное разным клиентам             |
| `Accept`                | запрос         | какие форматы клиент готов принять (`text/html`, `application/json`) |
| `Content-Type`          | оба            | формат тела: [[HTML-документ и DOM-дерево\|HTML]], [[Слабоструктурированные данные и JSON\|JSON]], форма, картинка                             |
| `Location`              | ответ          | куда идти при 3xx-редиректе                                          |
| `Cache-Control`         | ответ          | можно ли и сколько кэшировать                                        |
| `Set-Cookie` / `Cookie` | ответ / запрос | см. ниже                                                             |

## Cookies

HTTP не помнит прошлых запросов, поэтому сервер выдаёт клиенту "жетон": заголовок `Set-Cookie: session=abc123` — и браузер сам прикладывает `Cookie: session=abc123` ко всем следующим запросам на этот домен[^2]. Так работают логины, корзины и, увы, сквозная слежка рекламных сетей (third-party cookies — куки чужого домена, подгруженного на странице)

[^2]: Название — от "magic cookie" из юникс-жаргона: непрозрачный кусочек данных, который получил и вернул не разглядывая. В [[Аутентификация и сессии|модуле 10]] сделаем свои сессии на cookies

## HTTPS

**HTTPS** (HTTP Secure) = HTTP внутри шифрованного туннеля **TLS** (Transport Layer Security). Даёт три гарантии: никто по пути не читает (конфиденциальность), не подменяет (целостность), и сервер — тот, за кого себя выдаёт (сертификат, подписанный доверенным центром). До первой строки HTTP клиент и сервер делают **TLS-рукопожатие** — договариваются о ключах; его видно в `curl -v https://…`

> [!tip] Что всё-таки видно снаружи
> Провайдер видит IP сервера и (пока что) имя хоста из этапа **SNI** (Server Name Indication) рукопожатия, но не путь, не заголовки и не тело. Поэтому `http://` для чего угодно с паролями — дисквалификация: логин уезжает открытым текстом

## Версии HTTP

| Версия | Год | Главное |
|---|---|---|
| 0.9–1.0 | 1991–96 | одно соединение = один запрос |
| **1.1** | 1997 | keep-alive (соединение переиспользуется), `Host`, chunked. До сих пор жив — его говорит `curl` по умолчанию |
| **2** | 2015 | бинарный кадр, мультиплексирование: много запросов параллельно в одном соединении |
| **3** | 2022 | поверх [[Протокол UDP\|QUIC]] ([[Протокол UDP\|UDP]] вместо TCP) — быстрее устанавливается, не страдает от потери одного пакета |

Для прикладного кода семантика одна и та же: методы, коды и заголовки не меняются — меняется транспорт под ними. Какую версию согласовал браузер, видно в DevTools → Network → колонка Protocol ([[DevTools]])
