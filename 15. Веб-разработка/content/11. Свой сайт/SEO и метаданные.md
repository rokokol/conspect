# SEO и метаданные
**SEO** (Search Engine Optimization — поисковая оптимизация) — набор практик, делающих страницу понятной машинам: краулерам поисковиков и ботам соцсетей, читающим [[HTML-документ и DOM-дерево|HTML]] без человека. Львиная доля SEO — не трюки, а гигиена: [[Семантическая разметка|семантика]], скорость ([[Производительность страницы|Core Web Vitals]] — официальный фактор ранжирования Google), честные метаданные

## Минимум в head

```html
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Колода — интервальные карточки</title>          <!-- вкладка + синяя ссылка в выдаче -->
  <meta name="description" content="Учи что угодно карточками с интервальным повторением">
  <link rel="canonical" href="https://deck.example.com/">  <!-- какой URL считать главным -->
</head>
```

`<title>` и `meta description` — твой сниппет в выдаче: заголовок-ссылка и текст под ним (описание поисковик может и переписать, если сочтёт нерелевантным)

`viewport` из [[HTML-документ и DOM-дерево|модуля 02]] здесь снова: страницы без него Google помечает как non-mobile-friendly и ранжирует ниже — индексация давно mobile-first

`canonical` гасит дубли: `?utm_source=…`, `/index.html` и `/` — один контент, каноничным объявляется один [[URL и адресация|URL]], иначе поисковик делит вес страницы между копиями

## Open Graph

Ссылка, кинутая в Telegram или Discord, разворачивается в карточку с картинкой — это **Open Graph**, протокол мета-тегов от Facebook (2010), стандарт де-факто для всех мессенджеров:

```html
<meta property="og:title" content="Колода — интервальные карточки">
<meta property="og:description" content="Учи что угодно с интервальным повторением">
<meta property="og:image" content="https://deck.example.com/preview.png">   <!-- абсолютный URL! -->
<meta property="og:type" content="website">
```

> [!tip] Превью проверяется до публикации
> `og:image` требует абсолютный URL (бот соцсети тянет картинку со своего сервера) и кэшируется агрессивно. Валидаторы показывают карточку и сбрасывают кэш: в Telegram — бот @WebpageBot, у остальных — свои debug-страницы. Классический прокол "обновил картинку, а везде старая" — это их кэш, а не твоя ошибка

## JSON-LD

Шаг глубже мета-тегов — **структурированные данные**: блок [[Слабоструктурированные данные и JSON|JSON]] по словарю schema.org, из которого поисковик собирает обогащённые сниппеты (звёзды рейтинга, хлебные крошки, карточки статей):

```html
<script type="application/ld+json">
{ "@context": "https://schema.org", "@type": "WebApplication",
  "name": "Колода", "applicationCategory": "EducationalApplication" }
</script>
```

Для приложения это косметика, для контентных сайтов (статьи, рецепты, товары) — заметная разница в кликабельности выдачи. Проверяется гугловским Rich Results Test

## Структура для краулера

- **один `<h1>`** на страницу; `<h2>`/`<h3>` — иерархия разделов, а не размер шрифта
- **`alt` у картинок** — что изображено ([[Доступность|та же работа]] окупается дважды)
- **текст ссылок самодостаточен** — "читать про интервальные повторения", не "кликните сюда"
- осмысленные URL — `/decks/spanish`, не `/p?id=8f3a`

## Файлы для роботов

| Файл | Роль |
|---|---|
| `robots.txt` | что можно и нельзя обходить (`Disallow: /admin`) — лежит в `public/` |
| `sitemap.xml` | карта всех URL для краулера — генерируется при сборке |
| `manifest.json` | имя и иконки для установки как приложения ([[Tauri\|PWA]]) |

`robots.txt` — просьба, а не защита: вежливые краулеры слушаются, скрейперы — нет; закрытое должно быть закрыто [[Аутентификация и сессии|аутентификацией]]

## Потолок клиентского рендеринга

Подводный камень нашей архитектуры: [[Каркас сайта на Vite|сайт на Vite]] отдаёт почти пустой `index.html`, контент дорисовывает [[Типы и коэрция|JS]] [[DOM API|через DOM]]. Краулеры и боты видят *исходный* HTML — до JS там пусто[^1]. Google исполняет JS, но вторым проходом — очередь на рендеринг доходит с задержкой от часов до недель; Telegram и большинство соц-ботов не исполняют вовсе, потому og-теги обязаны лежать в статическом HTML

Отсюда **SSR** (Server-Side Rendering — HTML собирается сервером на каждый запрос) и **SSG** (Static Site Generation — все страницы собраны заранее при билде): фреймворки Next.js, Astro, SvelteKit отдают краулеру готовый HTML, а JS лишь оживляет его на клиенте — **гидратация**

Наш чистый клиентский рендер идеален для приложения за логином (SEO не нужно); контентному сайту — блогу, лендингу, магазину — выбирают SSR/SSG. Знать эту развилку важнее, чем любой конкретный фреймворк

[^1]: Проверка в одну команду: `curl -s https://твой-сайт | grep '<h1'` — ровно то, что видит краулер. Пусто — значит, для SEO нужен SSR/SSG. Тот же трюк разоблачает чужие сайты: curl показывает, отдают ли они готовый HTML или пустой каркас под JS
