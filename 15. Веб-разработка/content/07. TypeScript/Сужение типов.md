# Сужение типов
**Сужение** (narrowing) — [[Система типов TypeScript|TS]] читает обычные рантайм-проверки в коде и уточняет тип внутри ветки. Никакого спец-синтаксиса: правильно написанный [[Типы и коэрция|JS]] сужается сам — компилятор просто умеет следить за логикой

```ts
function render(value: string | number | null) {
  if (value === null) return;            // дальше: string | number
  if (typeof value === "number") {
    return value.toFixed(2);             // тут: number
  }
  return value.toUpperCase();            // а тут остался только string
}
```

## Стражи

| Проверка | Сужает |
|---|---|
| `typeof x === "string"` | примитивы |
| `x === null`, `x == null`, `if (x)` | null/undefined (truthiness — помни про `0` и `""` из [[Типы и коэрция|falsy]]!) |
| `Array.isArray(x)` | массив |
| `x instanceof Map` | классы |
| `"field" in x` | объект по наличию поля |
| `x === "idle"` | литералы union |

> [!warning] Сужение живёт только там, где TS видит поток управления
> Проверил — и вызвал колбэк? Внутри колбэка сужение сброшено (вдруг переменная изменилась между делом). Лекарство: сохранить в const до проверки. По той же причине сужение не работает через границы функций — для этого нужны predicates ниже

## Дискриминированные union

Общее литеральное поле-ярлык (**дискриминант**) превращает union в безопасную "алгебраическую" структуру:

```ts
type FetchState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: Card[] }
  | { status: "error"; error: string };

function view(s: FetchState) {
  switch (s.status) {
    case "success": return renderCards(s.data);   // data есть ТОЛЬКО здесь
    case "error":   return showError(s.error);
    …
  }
}
```

Поля привязаны к вариантам: `data` невозможно тронуть, не доказав `status === "success"` — состояние "error, но почему-то с data" непредставимо. Принцип **make illegal states unrepresentable**: моделируй состояния так, чтобы ерунда не компилировалась, — это заменяет пачку рантайм-проверок[^1]

[^1]: Паттерн — прямой потомок алгебраических типов данных (ADT, algebraic data types) из ML (Meta Language) и Haskell, где он существует с 1970-х как sum types с pattern matching. TS воспроизвёл его на switch и литералах — один из примеров, как функциональщина десятилетиями просачивается в мейнстрим

### Исчерпывающий switch

```ts
default:
  const _exhaustive: never = s;   // добавили новый вариант в union и забыли ветку?
  throw new Error("unreachable"); // ← эта строка перестанет компилироваться
```

`never` — "сюда не должно доходить": если все варианты разобраны, `s` в default имеет тип never и присваивание легально; появился неразобранный вариант — ошибка компиляции точно в этом месте. Бесплатный чек-лист при эволюции типов

## Свои стражи

```ts
function isCard(x: unknown): x is Card {
  return typeof x === "object" && x !== null && "front" in x && "back" in x;
}

const raw: unknown = JSON.parse(localStorage.getItem("deck") ?? "[]");
if (Array.isArray(raw) && raw.every(isCard)) {
  // raw: Card[] — граница «грязный мир → типизированный код» пройдена
}
```

Возвращаемый тип `x is Card` — **предикат**: true из функции сужает тип у вызывающего. Это ручная граница доверия — компилятор верит твоей проверке на слово, поэтому проверка обязана быть честной. Все входы приложения (fetch, localStorage, файлы) проходят через такие ворота; в больших проектах их генерируют библиотеки схем (zod и родня — [[Дизайн REST API|встретим в модуле 10]])

> [!tip] satisfies — проверить, не расширяя
> ```ts
> const config = { port: 3000, host: "localhost" } satisfies ServerConfig;
> ```
> `satisfies` (2022) проверяет соответствие типу, но сохраняет точный выведенный тип значения (port остаётся literal 3000, а не расплывается в number). Разница с `: ServerConfig` тонкая, но в конфигах и словарях именно она даёт лучшее автодополнение
